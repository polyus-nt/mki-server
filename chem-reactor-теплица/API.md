# HTTP API теплицы-химреактора

Адрес по умолчанию **http://127.0.0.1:8001**, Swagger `/docs`, ReDoc `/redoc`,
машиночитаемая схема `/openapi.json`. Запуск и сборка: [README.md](README.md).
Это отдельный сервис, не дополнение фаблаб-API на порте 8000.

Все индексы начинаются с 0. GET читает, POST управляет и требует JSON
с `Content-Type: application/json`. Успех — HTTP 200 и JSON.
Токенов нет: User/Admin — назначение методов, **не проверка прав**.
Любой клиент, имеющий доступ к серверу, может вызвать все команды.

## Методы

| Функция | Метод и полный путь | Индекс / тело |
| --- | --- | --- |
| `get_temp(idx)` | GET `/api/v1/temperature/{idx}` | 0..1 |
| `get_pressure(idx)` | GET `/api/v1/pressure/{idx}` | 0..1 |
| `get_humidity(idx)` | GET `/api/v1/humidity/{idx}` | 0..1 |
| `get_gas(idx)` | GET `/api/v1/gas/{idx}` | MQ-2, 0..1 |
| `get_door_state(idx)` | GET `/api/v1/doors/{idx}/state` | 0..1 |
| `get_pwm(idx)` | GET `/api/v1/fans/{idx}/pwm` | 0..1 |
| `set_pwm(idx, pwm)` | POST `/api/v1/fans/{idx}/pwm` | 0..1, `{"pwm":100}` |
| `get_rpm(idx)` | GET `/api/v1/fans/{idx}/rpm` | 0..1 |
| `get_door_lock()` | GET `/api/v1/lock/state` | Без индекса |
| `set_door_lock(lock_state)` — Admin | POST `/api/v1/admin/lock` | `{"lock_state":true}` |
| `get_relay_level()` | GET `/api/v1/relay-fan/level` | Без индекса |
| `set_relay_level(level)` | POST `/api/v1/relay-fan/level` | `{"level":7}` |
| Состояние сервиса | GET `/health` | Без аппаратного опроса |
| Состав конфигурации | GET `/api/v1/capabilities` | Без аппаратного опроса |
| Проверка хаба | GET `/api/v1/hub/probe` | Проверяет только хаб, не нижние платы |

Пылесоса, VOC, пыли, вентиляторов 2..5 и независимо управляемых замков здесь нет.
Все тела POST обязательны, лишние поля запрещены. PWM и level в теле —
строго целые числа, не строки, дроби или boolean. `lock_state` — строго boolean.
Некорректный HTTP-запрос отклоняется до обращения к аппаратуре.

## Показания и единицы

Все примеры ниже иллюстративные, не измерения реального стенда.
Температура BMP280, давление BMP280 и влажность DHT11:

```json
{"idx":0,"value":23.45,"unit":"degC","valid":true,"fresh":true,"age_ms":123,"received_at":"2026-10-10T00:00:00Z"}
```

| Поле / показание | Значение |
| --- | --- |
| `value` температуры | Градусы Цельсия, `unit="degC"` |
| `value` давления | Целое число паскалей, `unit="Pa"`; разделить на 100 для гПа |
| `value` влажности | Относительная влажность 0..100, `unit="%RH"` |
| `valid` | Есть корректное сохранённое измерение; успешный HTTP-ответ содержит true |
| `fresh` | Новое измерение ещё не выдано через интерфейс чтения Arduino |
| `age_ms` | Возраст измерения на Arduino, мс; насыщается на 65534 |
| `received_at` | Время получения ответа сервером в UTC, не время измерения |

GET читает кэш Arduino, не запускает новое физическое измерение.
`fresh=false` допустим: измерение уже выдавалось или после ошибки сохраняется
старое корректное показание. Флаг общий для всех клиентов, включая TEST-консоль.
`fresh=true` не означает изменения числа и не гарантирует малого возраста.
Проверяйте `age_ms`; 65534 означает, что данные могут быть старше 65.534 секунды.
`valid=true` не гарантирует успешного обновления датчика в текущий момент.
У BMP280 свежесть температуры и давления раздельная.
Если корректного значения ещё нет, ответ — SENSOR_UNAVAILABLE, а не фиктивный ноль.
DHT11 опрашивается не чаще раза в 2 секунды; MQ-2 — примерно раз в секунду.

MQ-2, `GET /api/v1/gas/0`:

```json
{"idx":0,"adc":512,"voltage_mv":2502,"voltage_v":2.502,"valid":true,"fresh":false,"age_ms":800,"received_at":"2026-10-10T00:00:00Z"}
```

`adc` — 0..1023; `voltage_mv` — напряжение в мВ, `voltage_v` — то же в вольтах.
Прошивка рассчитывает напряжение с опорой 5000 мВ из BoardConfig.
**Это не ppm, не VOC Index и не идентификация конкретного газа.** Прогрев,
калибровка и преобразование в концентрацию здесь не реализованы.
ADC может быть корректным и при неподключённом аналоговом выходе.

## Вентиляторы Arduino

Индексы 0/1. Чтение PWM и ответ на его установку имеют одинаковый вид:

```json
{"idx":1,"value":100,"unit":"PWM 0..255","received_at":"2026-10-10T00:00:00Z"}
```

PWM — целое 0..255, не процент. PWM=0 отключает реле питания,
PWM>0 включает реле и устанавливает PWM. Значение в ответе — применённое
прошивкой, не электрическое измерение на выходе. Переданное значение применяется
без подмены; режимов отказа в химреакторе нет. RPM читается отдельно:

```json
{"idx":1,"value":1200,"unit":"rpm","received_at":"2026-10-10T00:00:00Z"}
```

RPM обновляется примерно раз в секунду. Немедленно после SET PWM он может
ещё отражать прежнее вращение. При старте Arduino PWM=0 и реле выключены;
при потере связи последнее применённое значение удерживается.
PID и температурных правил в прошивке нет.

## Релейный вентилятор lmp8

POST `/api/v1/relay-fan/level` с `{"level":7}`. Допустимо 0..10:
0 — все реле выключены, 1..10 — комбинации из
[PINOUT.md в tjc-sketch](../../tjc-sketch/chem-reactor-теплица/PINOUT.md).
Число — номер комбинации, не процент мощности.

Реле МС-ТЮК активны HIGH: HIGH включает, LOW выключает.
При каждой новой SET-команде все шесть реле выключаются (LOW), выдерживается
не менее 250 мс, затем применяется новая комбинация. Ответ выдаётся
**после применения**, не после постановки в очередь.
GET и успешный POST возвращают:

```json
{"level":7,"received_at":"2026-10-10T00:00:00Z"}
```

Это установленный уровень управления, не измеренная мощность/скорость.
При старте level=0. Потеря связи не отключает реле автоматически.
В химреакторе нет режимов неисправности; level — обычное управление мощностью.

## Двери и общий замок

GET `/api/v1/doors/0/state`:

```json
{"idx":0,"closed":true,"received_at":"2026-10-10T00:00:00Z"}
```

Два концевика на кнопочнице независимы. Контакт на GND трактуется как
закрытая дверь; соответствие физическому монтажу проверить на стенде.

POST `/api/v1/admin/lock` с `{"lock_state":true}` блокирует **оба** магнитных
замка, false разблокирует оба. Они подключены к одному выходу lmp8 1:
HIGH блокирует, LOW разблокирует. При запуске платы оба замка заблокированы
(`lock_state=true`). Кнопки 3 и 4 на кнопочнице открывают оба замка на 5 секунд;
таймер исполняется локально на lmp8 и работает без компьютера. Новое нажатие
перезапускает 5 секунд, удержание не продлевает. Явный `set_door_lock`
отменяет таймер: false оставляет оба замка разблокированными до следующего
действия. `get_door_lock` во время импульса возвращает false.
Концевики независимы: idx=0/1 соответствуют физическим пинам кнопочницы 1/2.
Их реальные показания не подменяются состоянием общего выхода замков.
Кнопочные команды остаются внутренними и не добавляют HTTP/MCP эндпоинтов.
Индекса в этом API нет, адреса `/locks/0` и `/locks/1` не используются.

Ответ POST:

```json
{"acknowledged":true,"received_at":"2026-10-10T00:00:00Z"}
```

GET `/api/v1/lock/state`:

```json
{"lock_output_enabled":true,"received_at":"2026-10-10T00:00:00Z"}
```

`lock_output_enabled=true` — выход блокировки включён (LOW).
Это не положение двери и не подтверждение физического удержания замком.
Положение дверей читать отдельно через концевики.

## Отсутствие режимов отказа

В химреакторе нет get_mode/set_mode. GET/POST /api/v1/admin/mode возвращают
HTTP 404 и не обращаются к аппаратуре. Бинарные команды 0x40/0x41 возвращают
UNKNOWN_COMMAND, не меняя PWM. Релейные уровни 0..10 — обычное управление
вентилятором lmp8, не имитация отказа. В ФабЛаб режимы отказа сохранены.

## Диагностика, очередь и ошибки

`/health` возвращает status, serial_open, queue_depth, queue_capacity, active,
recovering и last_response_at. HTTP 200/ready означает доступность worker/порта,
не исправность всех датчиков; при disconnected — HTTP 503.
`/capabilities` описывает chemreactor, protocol_version=2, каналы и их количество,
общий замок, релейный вентилятор и единственный actuator-шлюз 14.
Это конфигурация, не автоматическое обнаружение железа.

`/hub/probe` отправляет GET_TEMP idx=2, который хаб должен отклонить локально.
Успех: `{"responding":true,"expected_status":"INVALID_INDEX","received_at":"..."}`.
В этом диагностическом методе INVALID_INDEX ожидаем и не является HTTP-ошибкой.

Одна FIFO для всех аппаратных GET/POST. По умолчанию: 64 ожидающих + один активный,
до 30 секунд до начала обмена, до 5 секунд на обмен. HTTP ждёт конечный результат,
а не возвращает queued/job ID. Служебные методы порт не занимают.
Сервер не делает фоновых снимков всех датчиков и не повторяет команды.
Просроченное ожидание в очереди не отправляется на плату.

Отмена клиентом не прерывает начавшийся обмен. **Таймаут POST не доказывает,
что команда не выполнилась.** Сначала прочитайте PWM, level или lock/state,
потом решайте, нужна ли повторная команда. При потере связи оборудование
не останавливается автоматически. После разрыва COM-порта сервис перезапустить.

Ошибка аппаратуры/сервиса:

```json
{"error":{"code":"DEVICE_TIMEOUT","message":"Оборудование вернуло ошибку","device_status":7,"node":13,"command":"get_pressure","idx":0}}
```

`code` и `message` — основа, остальные поля зависят от ошибки.
Программно анализируйте code и HTTP-статус, не текст message.

| HTTP | code |
| --- | --- |
| 422 | INVALID_INDEX, INVALID_ARGUMENT |
| 501 | UNKNOWN_COMMAND, NOT_IMPLEMENTED |
| 503 | SENSOR_UNAVAILABLE, BUSY, QUEUE_FULL, DISCONNECTED, SHUTTING_DOWN |
| 504 | QUEUE_TIMEOUT (не отправлен), HOST_TIMEOUT (нет ответа хаба), DEVICE_TIMEOUT (нижний узел не ответил) |
| 502 | UNSUPPORTED_VERSION, INTERNAL_ERROR аппаратуры, REQUEST_ID_CONFLICT, INVALID_NODE, TRANSPORT_OVERFLOW |
| 500 | INTERNAL_ERROR worker сервера |

Неверные HTTP-аргументы дают 422 с массивом `detail` FastAPI, не `error`;
неверный путь — 404, неверный метод — 405. После некоторых транспортных ошибок
worker дренирует поздние байты до секунды тишины, максимум 3 секунды.

## PowerShell

```powershell
$apiBase = "http://127.0.0.1:8001"
Invoke-RestMethod "$apiBase/api/v1/gas/0"
Invoke-RestMethod "$apiBase/api/v1/fans/1/rpm"
Invoke-RestMethod "$apiBase/api/v1/lock/state"

# Реальное управление оборудованием:
Invoke-RestMethod "$apiBase/api/v1/fans/1/pwm" -Method Post `
  -ContentType "application/json" -Body '{"pwm":100}'
Invoke-RestMethod "$apiBase/api/v1/relay-fan/level" -Method Post `
  -ContentType "application/json" -Body '{"level":7}'
Invoke-RestMethod "$apiBase/api/v1/admin/lock" -Method Post `
  -ContentType "application/json" -Body '{"lock_state":true}'
```

Ручная консоль: `py -3 scripts/api_console.py`, примеры в [README.md](README.md).
`selftest` — только последовательные чтения: 20 запросов плюс OpenAPI;
fresh=false допустим, ошибки не прерывают оставшиеся проверки.
Коды выхода: 0 — успех, 1 — ошибка запроса/проверки, 2 — ошибка команды,
130 — прерывание пользователем. Для стандартных настроек клиентский таймаут 45 с.

## Общая шина и задержка запросов

Хаб автономно опрашивает кнопки открытия, даже без FastAPI.
Перед каждым аппаратным запросом сервис ждёт секунду тишины на общей
полудуплексной шине (не более 3 с); хаб оставляет 1.5 с между опросами.
Это ожидание предшествует exchange-timeout и добавляет задержку HTTP-вызову.
FIFO и единственный владелец COM-порта сохраняются. Используйте обновлённый
сервис и sensor_console: старый клиент без ожидания тишины может столкнуться
с автономным обменом. Дополнительные инициаторы на шине не допускаются.
