# Единый API: теплица-химреактор и химический реактор

Руководство для пользователей и разработчиков внешних приложений.
Актуально на 23 октября 2026 года, для ветки `feat/chemical-reactor-integration`
репозитория `tjc-commutator`. Документ самостоятельный: его можно пересылать отдельно.

## 1. Назначение и подключение

Теплица и химический реактор — **одна аппаратная система**. Один FastAPI-сервис
общается через один COM-порт с центральным хабом МС-ТЮК. Приложения обращаются
только к HTTP API; открывать COM-порт или формировать аппаратные пакеты не нужно.

В систему входят:

- Теплица: BMP280 ×2, DHT11 ×2, MQ-2 ×2, концевики ×2, PWM-вентиляторы ×2.
- lmp8: два магнитных замка на общем выходе и релейный вентилятор с уровнями 0..10.
- Реактор: три шаговых двигателя, три канала STM32 измерения/установки U/I,
  один общий датчик DS18B20, три информационных таймера и LCD.

Базовый адрес по умолчанию: **`http://127.0.0.1:8001`**.
Для удалённого подключения вместо `127.0.0.1` использовать адрес компьютера сервиса;
сервис должен быть явно настроен на сетевой доступ, а firewall — разрешать его.

| Адрес | Назначение |
| --- | --- |
| `/docs` | Интерактивная документация Swagger, выполнение запросов |
| `/redoc` | Документация в браузере |
| `/openapi.json` | Машиночитаемая спецификация фактически запущенного сервиса |
| `/panel` | HTML-панель ручного управления теплицей и реактором |

**Авторизации нет:** токены, пароли и `Authorization` не требуются. Префикс
`admin` обозначает назначение метода, а не проверку прав. Любой клиент с доступом
к сервису может запускать моторы, управлять вентиляторами, замками и уставками.
Не открывайте сервис в недоверенную сеть без внешнего ограничения доступа.

## 2. Общие правила

- `GET` читает состояние, `POST` отправляет команду.
- Тело `POST` — JSON с заголовком `Content-Type: application/json`.
- Все индексы начинаются с **0**. Для двух устройств: 0/1; для трёх: 0/1/2.
- Целочисленные параметры передаются JSON-числом, логические — `true`/`false`.
  Не заменять числа/boolean строками. Лишние поля в управляющих телах запрещены.
- Успешный запрос возвращает HTTP **200** и JSON.
- `received_at` — время получения ответа сервисом, ISO 8601 UTC, не время
  физического измерения. Для датчиков возраст измерения указан отдельно.
- Сервер последовательно обслуживает единую очередь. HTTP-запрос ждёт результата,
  а не получает немедленное «принято в очередь».
- Автоматических повторов управляющих запросов нет. При таймауте команда могла
  исполниться: сначала прочитайте состояние, не повторяйте её вслепую.

Во всех таблицах ниже пути добавляются к базовому адресу сервиса.

## 3. Проверка связи и возможностей

| Метод | Путь | Что проверяет |
| --- | --- | --- |
| GET | `/health` | Состояние сервиса/COM-порта, без аппаратного опроса |
| GET | `/api/v1/capabilities` | Состав и количество каналов, поддерживаемые функции |
| GET | `/api/v1/hub/probe` | Обмен ПК ↔ центральный хаб, без нижних плат |

Нормальный ответ `probe`:

```json
{
  "responding": true,
  "expected_status": "INVALID_INDEX",
  "received_at": "2026-10-23T16:56:53.413784+00:00"
}
```

`INVALID_INDEX` здесь намеренный: сервис посылает заведомо неверный индекс,
хаб сам отклоняет его, и это преобразуется в успешную проверку. Это не доказывает
исправность Arduino, датчиков или исполнительных устройств.

## 4. Датчики теплицы

Во всех методах этого раздела `idx` — **0 или 1**.

| Метод | Путь | Результат |
| --- | --- | --- |
| GET | `/api/v1/temperature/{idx}` | Температура BMP280, °C; `unit: "degC"` |
| GET | `/api/v1/pressure/{idx}` | Давление BMP280, Па; `unit: "Pa"` |
| GET | `/api/v1/humidity/{idx}` | Влажность DHT11, % RH; `unit: "%RH"` |
| GET | `/api/v1/gas/{idx}` | MQ-2: ADC и напряжение, **не ppm** |

Пример ответа температуры (иллюстрация, не измерение конкретного стенда):

```json
{
  "idx": 0,
  "value": 24.35,
  "unit": "degC",
  "valid": true,
  "fresh": true,
  "age_ms": 120,
  "received_at": "2026-10-23T17:00:00+00:00"
}
```

Качество измерения:

- `valid` — измерение корректно; отсутствие пригодного значения обычно возвращается ошибкой.
- `fresh` — признак свежего результата в аппаратном кэше; чтение может его сбросить.
  `false` не означает само по себе поломку датчика.
- `age_ms` — возраст физического измерения в миллисекундах. Оценивайте его вместе
  с `fresh`; частый HTTP-опрос не заставляет датчик измерять быстрее.

Ответ MQ-2:

```json
{
  "idx": 0,
  "adc": 512,
  "voltage_mv": 2502,
  "voltage_v": 2.502,
  "valid": true,
  "fresh": true,
  "age_ms": 100,
  "received_at": "2026-10-23T17:00:00+00:00"
}
```

ADC имеет диапазон 0..1023. Концентрация газа и конкретный состав смеси не
вычисляются. Наличие числа ADC само по себе не подтверждает исправность датчика.
VOC/пыль/пылесос к этой конфигурации не относятся, соответствующих методов нет.

## 5. Двери и магнитные замки

| Метод | Путь | Тело JSON | Назначение |
| --- | --- | --- | --- |
| GET | `/api/v1/doors/{idx}/state` | — | Концевик двери, `idx` 0/1 |
| GET | `/api/v1/lock/state` | — | Состояние общего управляющего выхода замков |
| POST | `/api/v1/admin/lock` | `{"lock_state": true}` | Заблокировать оба замка |
| POST | `/api/v1/admin/lock` | `{"lock_state": false}` | Разблокировать оба замка |

Пример двери: `{"idx":0,"closed":true,"received_at":"2026-10-23T17:00:00+00:00"}`.
`closed=true` означает замкнутый концевик, принятый за закрытую дверь.

Пример состояния замков:
`{"lock_output_enabled":true,"received_at":"2026-10-23T17:00:00+00:00"}`.
Здесь `true` означает включённую блокировку, **не HIGH на физическом пине**.
Выход общий для двух замков, поэтому у методов замка **нет индекса**.
Состояние выхода не доказывает физическое положение двери или срабатывание замка:
для положения двери отдельно читайте концевики.

Успех установки: `{"acknowledged":true,"received_at":"2026-10-23T17:00:00+00:00"}`.
Команда HTTP разблокировки сама по себе не означает двухсекундный импульс.
Автономно кнопки на пинах 3/4 кнопочницы открывают оба замка на **2 секунды**;
хаб опрашивает счётчики нажатий раз в 2 секунды. На старте замки заблокированы.

## 6. Два PWM-вентилятора теплицы

`idx` — **0 или 1**, PWM — целое **0..255**.

| Метод | Путь | Тело JSON | Назначение |
| --- | --- | --- | --- |
| GET | `/api/v1/fans/{idx}/pwm` | — | Применённое значение PWM |
| POST | `/api/v1/fans/{idx}/pwm` | `{"pwm": 150}` | Установить PWM |
| GET | `/api/v1/fans/{idx}/rpm` | — | Измеренные обороты в минуту |

PWM=0 выключает вентилятор. PWM=255 — максимальное управляющее значение.
PWM — не обороты и не проценты. Фактическую работу проверять чтением RPM.

Пример ответа GET/POST PWM:

```json
{
  "idx": 1,
  "value": 150,
  "unit": "PWM 0..255",
  "received_at": "2026-10-23T17:00:00+00:00"
}
```

RPM имеет аналогичный формат, например `value: 1800`, `unit: "rpm"`.
Потеря связи не выключает вентиляторы автоматически: последнее PWM удерживается.
Режимов неисправности `get_mode`/`set_mode` **в химтеплице нет**.

## 7. Релейный вентилятор lmp8

Это отдельный вентилятор, не один из двух PWM-каналов.

| Метод | Путь | Тело JSON | Назначение |
| --- | --- | --- | --- |
| GET | `/api/v1/relay-fan/level` | — | Текущий уровень |
| POST | `/api/v1/relay-fan/level` | `{"level": 7}` | Установить уровень 0..10 |

Уровень — целое 0..10, **0 выключает**. Индекса нет.
Ответ: `{"level":7,"received_at":"2026-10-23T17:00:00+00:00"}`.
Перед новым уровнем все шесть реле выключаются на 250 мс, затем включается
нужная комбинация. Уровни — аппаратная таблица, не проценты мощности и не
гарантированно линейная шкала. Успешный ответ подтверждает применённый уровень,
но не измеренную скорость этого вентилятора.

## 8. Общая температура химического реактора

| Метод | Путь | Результат |
| --- | --- | --- |
| GET | `/api/v1/reactor/temperature` | Общий DS18B20 реактора, °C |

Датчик один, индекс в URL не передаётся. Не путать с двумя BMP280 теплицы.
Ответ содержит `idx: 0`, `value`, `unit: "degC"`, `valid`, `fresh`, `age_ms`,
`received_at`, как остальные температурные измерения.

## 9. Шаговые двигатели реактора

Три двигателя: `idx` — **0, 1 или 2**. Команды задают **непрерывное движение**,
а не количество оборотов. Двигатель работает до следующей команды скорости,
остановки, сброса платы или отключения питания. Опрос датчиков продолжается.

| Метод | Путь | Тело JSON | Назначение |
| --- | --- | --- | --- |
| GET | `/api/v1/reactor/motors/{idx}/state` | — | Скорость, настройки и диагностика генерации STEP |
| POST | `/api/v1/reactor/motors/{idx}/sps` | `{"rate": 1500}` | Частота импульсов STEP в секунду |
| POST | `/api/v1/reactor/motors/{idx}/rpm` | `{"rate": 100}` | Обороты в минуту |
| POST | `/api/v1/reactor/motors/{idx}/stop` | Без тела | Остановить выбранный двигатель и отключить драйвер |
| POST | `/api/v1/reactor/motors/stop` | Без тела | Остановить и отключить все три двигателя |
| POST | `/api/v1/reactor/motors/{idx}/enable` | `{"enabled": true}` | Включить удержание остановленного двигателя |
| POST | `/api/v1/reactor/motors/{idx}/enable` | `{"enabled": false}` | Отключить остановленный драйвер |
| POST | `/api/v1/reactor/motors/{idx}/microstep` | `{"divisor": 4}` | Установить микрошаг 1/4 |

### Скорость и микрошаги

- `rate` — JSON-число, не строка, до трёх знаков после точки.
- Положительное/отрицательное значение задаёт направление. Физическое направление
  зависит от подключения двигателя. Ноль останавливает и отключает драйвер.
- SPS означает один импульс STEP, то есть выбранный микрошаг, а не полный шаг двигателя.
- Диапазон SPS: **−7000..7000**. Для RPM HTTP-валидатор также принимает
  −7000..7000, но прошивка дополнительно проверяет предел 7000 STEP/с после
  пересчёта: допустимый RPM существенно меньше и зависит от микрошага.
- Пересчёт: `SPS = RPM × full_steps_per_rev × microstep / 60`.
  Для 200 полных шагов/оборот и 1/4 шага: 100 RPM ≈ 1333,333 STEP/с;
  программный предел 525 RPM. Это не гарантия механической работоспособности.
- Микрошаг: `divisor` — целое **4, 8, 16 или 32**, то есть 1/4, 1/8, 1/16, 1/32.
  Менять его можно только у остановленного **и отключённого** драйвера.
  Сначала выполните `stop`, затем `microstep`, затем новую команду скорости.
- `enable` не является командой остановки: при движении возвращается BUSY.
  Для остановки использовать `stop`.
- Разгон программный, параметры находятся в прошивке; отдельного HTTP-параметра
  ускорения нет. Повтор той же скорости не начинает разгон заново.

POST скорости, остановки, enable и microstep возвращают `acknowledged: true`
и `received_at`. Это подтверждение исполнения команды прошивкой, не подтверждение
фактического вращения вала или отсутствия пропущенных шагов.

### Ответ состояния двигателя

```json
{
  "idx": 0,
  "current_sps": 1333.333,
  "target_sps": 1333.333,
  "enabled": true,
  "running": true,
  "ramping": false,
  "microstep": 4,
  "full_steps_per_rev": 200,
  "max_late_us": 0,
  "resyncs": 0,
  "current_rpm": 99.999975,
  "target_rpm": 99.999975,
  "measured": false,
  "received_at": "2026-10-23T17:00:00+00:00"
}
```

`current_sps`/RPM — расчётные параметры генератора, **не энкодерное измерение**.
`max_late_us` и `resyncs` — диагностика генерации импульсов, не счётчики
механически потерянных шагов. Метод делает три последовательных аппаратных чтения,
поэтому ответ не является атомарным снимком на один момент времени.

**Stop проходит ту же очередь, что остальные запросы. Это не аппаратная аварийная
остановка:** для опасной установки нужна независимая аппаратная защита.

## 10. Напряжение и ток трёх каналов STM32

`idx` — **0, 1 или 2**. Чтения фактических величин и уставок — разные операции.

| Метод | Путь | Тело JSON / единицы |
| --- | --- | --- |
| GET | `/api/v1/reactor/stm/{idx}/voltage` | Считанное напряжение, мВ |
| GET | `/api/v1/reactor/stm/{idx}/current` | Считанный ток, мА |
| GET | `/api/v1/reactor/stm/{idx}/voltage/setpoint` | Уставка напряжения, мВ |
| GET | `/api/v1/reactor/stm/{idx}/current/setpoint` | Уставка тока, мА |
| POST | `/api/v1/reactor/stm/{idx}/voltage/setpoint` | `{"millivolts": 2500}` |
| POST | `/api/v1/reactor/stm/{idx}/current/setpoint` | `{"milliamps": 12.5}` |

Напряжение уставки: целое **0..6000 мВ**. Ток уставки: JSON-число **0..50 мА**,
до трёх знаков после точки. Например, 12.5 означает **12,5 мА**, не амперы.

GET и успешные POST уставок возвращают:

```json
{
  "idx": 0,
  "value": 12.5,
  "unit": "mA",
  "received_at": "2026-10-23T17:00:00+00:00"
}
```

Для напряжения `unit: "mV"`; считанное напряжение может быть дробным и знаковым.
Запись уставки не доказывает, что на выходе достигнуты такие U/I: после записи
отдельно считайте измеряемую величину. API-команды `off` для STM32 нет;
нулевая уставка не означает гарантированного физического обесточивания.

## 11. Три информационных таймера

`idx` — **0, 1 или 2**. Таймеры независимы, длительность — целые **0..65535 минут**.

| Метод | Путь | Тело JSON | Назначение |
| --- | --- | --- | --- |
| GET | `/api/v1/reactor/timers/{idx}` | — | Прочитать расчётный остаток и состояние |
| POST | `/api/v1/reactor/timers/{idx}` | `{"minutes": 15}` | Запустить/перезапустить на 15 минут |
| POST | `/api/v1/reactor/timers/{idx}` | `{"minutes": 0}` | Отменить и очистить таймер |

Установка возвращает `acknowledged: true` и `received_at`. Чтение:

```json
{
  "idx": 0,
  "duration_minutes": 15,
  "remaining_seconds": 899,
  "state": "running",
  "received_at": "2026-10-23T17:00:00+00:00"
}
```

Состояния: `idle` — не запущен/отменён; `running` — отсчёт;
`finished` — завершён. Остаток округляется вверх до секунды.
Окончание таймера **не останавливает моторы, не меняет U/I и не переключает выходы**.

В текущей конфигурации Due + отдельная UNO экранов отсчёт для LCD выполняет
сама UNO. Она продолжает его при пропаже связи/сбросе Due. API читает расчётное
зеркало на Due, а не подтверждённый остаток UNO: обратной связи UNO → Due нет.
После сбросов эти состояния могут расходиться. Перезапуск UNO теряет её
энергозависимый отсчёт; повтор последней команды может запустить длительность заново.
В варианте Mega с локальными LCD таймер остаётся на Mega.

## 12. Готовые HTTP-примеры

Примеры для Linux/macOS. В PowerShell используйте `curl.exe`, а не псевдоним
`curl`; удобнее также выполнять POST через `/docs` или `/panel`.

```bash
# Только проверка хаба.
curl http://127.0.0.1:8001/api/v1/hub/probe

# Температура первого датчика теплицы.
curl http://127.0.0.1:8001/api/v1/temperature/0

# Вентилятор 0: установить PWM, затем выключить.
curl -X POST http://127.0.0.1:8001/api/v1/fans/0/pwm \
  -H 'Content-Type: application/json' -d '{"pwm":150}'
curl -X POST http://127.0.0.1:8001/api/v1/fans/0/pwm \
  -H 'Content-Type: application/json' -d '{"pwm":0}'

# Первый шаговый двигатель: 100 RPM, затем остановить.
curl -X POST http://127.0.0.1:8001/api/v1/reactor/motors/0/rpm \
  -H 'Content-Type: application/json' -d '{"rate":100}'
curl -X POST http://127.0.0.1:8001/api/v1/reactor/motors/0/stop

# STM32, канал 0: установить 2500 мВ и прочитать измерение.
curl -X POST http://127.0.0.1:8001/api/v1/reactor/stm/0/voltage/setpoint \
  -H 'Content-Type: application/json' -d '{"millivolts":2500}'
curl http://127.0.0.1:8001/api/v1/reactor/stm/0/voltage

# Первый таймер — 15 минут.
curl -X POST http://127.0.0.1:8001/api/v1/reactor/timers/0 \
  -H 'Content-Type: application/json' -d '{"minutes":15}'
```

Включающие команды реально воздействуют на оборудование. Проверять под
наблюдением оператора, предварительно убедившись в безопасности силовой части.

## 13. Ошибки и таймауты

Пример аппаратной ошибки:

```json
{
  "error": {
    "code": "DEVICE_TIMEOUT",
    "message": "Оборудование вернуло ошибку",
    "device_status": 7,
    "node": 14,
    "command": "get_pwm",
    "idx": 1
  }
}
```

| HTTP | Код / причина | Смысл |
| --- | --- | --- |
| 422 | Ошибка валидации JSON/URL | Неверный тип, диапазон, обязательное или лишнее поле; запрос не отправлен |
| 422 | `INVALID_INDEX`, `INVALID_ARGUMENT` | Оборудование отклонило аргументы |
| 503 | `SENSOR_UNAVAILABLE` | Нет пригодного измерения |
| 503 | `BUSY` | Узел занят или операция запрещена текущим состоянием |
| 503 | `QUEUE_FULL` | Очередь сервера заполнена |
| 503 | `DISCONNECTED`, `SHUTTING_DOWN` | Порт/worker недоступен или сервис останавливается |
| 504 | `QUEUE_TIMEOUT` | Запрос не дождался отправки из очереди |
| 504 | `HOST_TIMEOUT` | Нет разрешения/подходящего ответа хаба в срок |
| 504 | `DEVICE_TIMEOUT` | Хаб/шлюз не дождался нижнего узла |
| 501 | `UNKNOWN_COMMAND`, `NOT_IMPLEMENTED` | Команда не поддерживается |
| 502 | Прочие аппаратные/транспортные ошибки | Несовместимость, сбой протокола, переполнение и т. п. |
| 500 | Внутренняя ошибка worker | Программный сбой сервиса |

Ошибка FastAPI валидации имеет стандартное поле `detail`, а не `error`:
клиент должен обрабатывать оба формата и проверять HTTP-статус.
Не все ошибки содержат `node`, `idx` или `device_status`.

В `HOST_TIMEOUT` могут быть `rx_bytes` и `command_sent`:

- `rx_bytes=0`, `command_sent=false`: ПК не получил приглашения хаба, команда
  не отправлена. Проверять COM-порт, питание, прошивку и связь ПК ↔ хаб.
- `command_sent=true`: запрос был отправлен; отсутствие ответа не означает откат.
- `DEVICE_TIMEOUT`: пришёл ответ с аппаратной ошибкой; искать нужно ниже хаба,
  но также проверить соответствие прошивок выбранной теплице.

По умолчанию FIFO содержит до 64 ожидающих запросов, ожидание в ней — до 30 с,
один аппаратный обмен — до 5 с. Метод состояния двигателя делает три обмена.
Клиентский таймаут должен учитывать очередь и состав операции; консоль по
умолчанию использует 45 с. Не запускайте частый параллельный опрос десятками
потоков: он создаст очередь, а не ускорит физическую шину.

## 14. Ручная консоль и проверка API

В репозитории `tjc-commutator`, ветка `feat/chemical-reactor-integration`,
из папки `chem-reactor-теплица`:

```text
python3 scripts/api_console.py
```

На Windows: `py -3 scripts/api_console.py`. Консоль обращается к HTTP-сервису
на 8001 и не открывает COM-порт. Примеры команд:

```text
probe
temp 0
pressure 1
humidity 0
gas 1
door 0
set_pwm 0 150
pwm 0
rpm 0
set_pwm 0 0
lock
set_door_lock 1
relay
set_relay_level 0
reactor_temp
motor 0
motor_micro 0 1/4
motor_rpm 0 100
motor_stop 0
motor_stop
stm 0 get_u
stm 0 set_u 2500
stm 0 get_i
stm 0 set_i 12.5
timer 0
set_timer 0 15
set_timer 0 0
selftest
```

`selftest` читает OpenAPI и последовательно проверяет все GET-методы и индексы.
Выходы не переключает, POST не проверяет. Отсутствующие платы дадут ошибки их
каналов. Он проверяет доступность API/чтений, не калибровку, механику или силовые цепи.
Для другого сервера: `python3 scripts/api_console.py --url http://АДРЕС:8001`.

## 15. Запуск сервиса и совместимость

Из папки `tjc-commutator/chem-reactor-теплица`:

```bash
python3 -m venv .venv
.venv/bin/python -m pip install -r requirements.txt
.venv/bin/python -m hub_service --serial-port /dev/ttyACM0
```

Windows:

```powershell
py -3 -m venv .venv
.venv\Scripts\python.exe -m pip install -r requirements.txt
.venv\Scripts\python.exe -m hub_service --serial-port COM15
```

Выбрать порт USB-интерфейса МС-ТЮК, не USB Due/UNO. Все другие владельцы
порта закрыть. Нужен один экземпляр сервиса с одним worker, без reload.
COM можно также передать через `MSTJUK_SERIAL_PORT`.
Для сети явно добавить `--host 0.0.0.0` и ограничить доступ firewall.

Рабочая общая шина МС-ТЮК — **115200, 8N1**, с READY → CLAIM → GRANT.
Хаб и остальные платы должны иметь совместимые рабочие прошивки химтеплицы.
Диагностические `hub-test`/`buttons-test` на 9600 с этим сервисом не работают.
Прошивка ФабЛаба тоже не подходит: отличаются каналы, маршруты и поддерживаемые команды.

Физические роли: центральный хаб 12, sensors-шлюз 13, actuator-шлюз 14,
кнопочница 15, lmp8 16, шлюз реактора 17; компьютер — 99.
Прошивки МС-ТЮК: `tjc-sketch/chem-reactor-теплица/`.
Arduino sensors: `arduino-sensor/chem-reactor-теплица/arduino-sensors/`.
Вентиляторы: `arduino-actuator/chem-reactor-теплица/arduino-actuator/`.
Due и UNO экранов: `arduino-actuator/chem-reactor-теплица/chemical-reactor/`.

Отсутствуют: VOC, пыль, пылесос, режимы отказов вентиляторов, автоматическая
установка температуры теплицы, управление точным количеством оборотов мотора,
аппаратная обратная связь по положению моторов и отдельная STM32-команда OFF.
