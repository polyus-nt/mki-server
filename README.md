# МС-ТЮК Hub API — FastAPI

Самостоятельный Python-сервис для **фаблаб-теплицы**: HTTP → FIFO → COM-порт →
центральный хаб МС-ТЮК → аппаратный узел. Ветка `feat/fastapi-hub-service`
содержит только сервис, тесты и документацию. Предыдущий Rust-проект и прошивки
сохранены в истории и ветке `feat/hardware-api-firmware`, но не нужны для запуска сервиса.

User API: чтения и установка PWM шести вентиляторов. Admin API: режим
неисправности, независимые замки и пылесос. Это логические группы методов,
**без авторизации**: все методы доступны напрямую, без токенов и заголовков.
Сырые пакеты не экспортируются. Релейный вентилятор химреактора отключён.

**Полное руководство для пользователей API:** [docs/API.md](docs/API.md) —
все методы, аргументы, ответы, единицы измерения, ошибки и примеры для Windows.

## Запуск на Windows

Python 3.10+; в каталоге репозитория:

```powershell
git fetch origin
git switch feat/fastapi-hub-service
git pull
py -3 -m venv .venv
.venv\Scripts\python.exe -m pip install -r requirements.txt
.venv\Scripts\python.exe -m hub_service --serial-port COM15
```

Откройте Swagger: **http://127.0.0.1:8000/docs**.
COM15 — рабочий порт текущего стенда; при другом назначении укажите свой.
Закройте sensor_console, hub_test_console, commutator и другие программы,
владеющие этим портом. Нужны **рабочие** прошивки API v2, не тестовый byte-response хаб.

Пример PowerShell:

```powershell
Invoke-RestMethod http://127.0.0.1:8000/api/v1/hub/probe
Invoke-RestMethod http://127.0.0.1:8000/api/v1/pressure/0
Invoke-RestMethod http://127.0.0.1:8000/api/v1/doors/0/state
Invoke-RestMethod http://127.0.0.1:8000/api/v1/locks/1/state
Invoke-RestMethod http://127.0.0.1:8000/api/v1/vacuum/state
```

`hub/probe` ожидает INVALID_INDEX от самого хаба: нижние узлы не участвуют.
Он подтверждает обмен с хабом, но не наличие датчиков или состояние исполнительных устройств.
`/health` проверяет состояние сервиса/порта, не запускает аппаратный опрос.

## Ручная консоль и selftest

В другом терминале, пока FastAPI запущен:

```powershell
py -3 scripts/api_console.py
```

Консоли достаточно стандартного Python, установка библиотек не нужна.
Она общается по HTTP и **не открывает COM-порт**. Примеры ввода:

```text
api> probe
api> temp 0
api> pressure 2
api> voc 1
api> humidity 0
api> dust 1
api> door 0
api> pwm 3
api> rpm 3
api> lock 1
api> vacuum
api> get_mode
api> set_pwm 4 100
api> set_mode 2 4
api> set_mode 0 4
api> set_door_lock 1 1
api> set_vacuum 1
api> set_vacuum 0
api> selftest
api> exit
```

`help` показывает команды; `get /api/v1/pressure/0` делает произвольный GET.
Ответы показываются в JSON с HTTP-статусом и временем ожидания.
`selftest` получает OpenAPI и последовательно проходит **все GET-методы API,
включая все допустимые индексы**: сейчас 34 запроса плюс получение OpenAPI.
Продолжает после ошибок и выводит список непрошедших запросов. HTTP-ошибка,
ошибка связи, неверный JSON, поле `error`/`detail` или `valid=false` — FAIL.
`fresh=false` не считается ошибкой: чтение кэшированного измерения допустимо.
Это проверка доступности API/оборудования, не калибровки датчиков и не физического
срабатывания замков. Никакие выходы не переключаются, повторов запросов нет.
Если часть плат не подключена, selftest честно покажет ошибки этих каналов.

Однократный запуск удобен для скриптов: код выхода 0 — успех, 1 — ошибка проверки,
2 — ошибка команды, 130 — прерывание пользователем.

```powershell
py -3 scripts/api_console.py --command selftest
py -3 scripts/api_console.py --command "temp 0"
py -3 scripts/api_console.py --url http://192.168.1.10:8000 --timeout 45
```

Admin-команды и полный selftest доступны сразу, дополнительная настройка
авторизации не нужна. Все команды используют тот же адрес сервера.
HTTP-таймаут по умолчанию 45 с включает ожидание в очереди сервера; если меняли
серверные таймауты, увеличьте `--timeout` клиента. После таймаута автоматического
повтора нет; сервер может ещё завершать уже начатый обмен.

## Эндпоинты

Чтения — GET, префикс `/api/v1`:

| Путь | Индекс | Результат |
| --- | --- | --- |
| `/temperature/{idx}` | 0..2 | температура BMP280, °C |
| `/pressure/{idx}` | 0..2 | давление BMP280, Па |
| `/voc/{idx}` | 0..1 | VOC Index SGP40, не ppm |
| `/humidity/{idx}` | 0..2 | влажность DHT11, % RH |
| `/dust/{idx}` | 0..1 | ADC и напряжение GP2Y1010AU0F, не концентрация |
| `/doors/{idx}/state` | 0..1 | `closed`, концевики кнопочницы |
| `/fans/{idx}/pwm` | 0..5 | применённый PWM 0..255 на Arduino |
| `/fans/{idx}/rpm` | 0..5 | измеренные RPM на Arduino |
| `/locks/{idx}/state` | 0..1 | состояние независимого выхода замка на lmp8 |
| `/vacuum/state` | без индекса | состояние выхода пылесоса на lmp8 |
| `/hub/probe` | без индекса | ответ самого хаба |
| `/capabilities` | без индекса | состав поддерживаемой фаблаб-конфигурации |
| `/admin/mode` | без индекса, Admin | `{mode, idx}`, в режиме0 idx=null |

Управление — POST, JSON body; отдельные функции аппаратного API:

| Метод API | HTTP путь | JSON body | Группа |
| --- | --- | --- | --- |
| `set_pwm(idx, pwm)` | `/api/v1/fans/{idx}/pwm` | `{"pwm":100}` | User |
| `set_mode(mode, idx)` | `/api/v1/admin/mode` | `{"mode":2,"idx":4}` | Admin |
| `set_door_lock(idx, lock_state)` | `/api/v1/admin/locks/{idx}` | `{"lock_state":true}` | Admin |
| `set_vacuum(mode)` | `/api/v1/admin/vacuum` | `{"mode":1}` | Admin |

PWM0..255, вентиляторы0..5; замки0..1. В `set_vacuum` mode0 выключает,
mode1 включает. В `set_mode`: mode0 нормальный, mode1 периодически меняет
физический PWM выбранного вентилятора через30с, mode2 искажает только его новые
команды PWM. Включение mode1 сразу задаёт случайный PWM. Единственный сценарий
неисправности координируется хабом между обеими Arduino. Для чтения/изменения
режима нужны обе платы; обычные команды живой платы не требуют второй.
При mode0 индекс0..5 обязателен, но игнорируется; последнее PWM удерживается.
`set_pwm` возвращает фактически применённое значение, в mode2 оно может
отличаться от запроса. Замок/пылесос возвращают `acknowledged=true`: подтверждение
команды, не доказательство физического срабатывания.
Не передавайте строковые числа, `true` вместо PWM или лишние JSON-поля — 422.

Вентиляторы0..3 находятся на первой UNO (шлюз14), 4/5 — на второй (шлюз17,
локально0/1). HTTP и компьютерный кадр по-прежнему используют единый node14;
перевод индексов делает хаб. Полная распиновка — `tjc-sketch/docs/PINOUT.md`;
краткая конфигурация и команды сборки — [docs/GREENHOUSES.md](docs/GREENHOUSES.md).

Замки теперь **на разных пинах**, поэтому имеют индексы 0/1. Пылесос один,
его публичный API индекса не содержит. `lock_output_enabled` — состояние выхода
управления, **не подтверждение физического срабатывания**. `closed` читается
отдельно с концевика. `enabled` пылесоса также не доказывает вращение двигателя.

Пример ответа давления (иллюстрация, не измерение стенда):

```json
{"idx":0,"value":100653,"unit":"Pa","valid":true,"fresh":true,"age_ms":123,"received_at":"2026-10-10T00:00:00Z"}
```

`age_ms` — возраст показания на плате, `fresh` — ещё не выданное новое измерение.
Повторный GET может вернуть прежнее значение с `fresh=false`. `received_at` —
время получения ответа компьютером. HTTP-слой не подставляет фиктивные измерения.

## Очередь и ошибки

Один worker сериализует физические обмены; все операции с портом, включая
открытие/закрытие, выполняет один выделенный поток. Async HTTP не блокируется
на UART: `/health` доступен и во время ожидания оборудования.
По умолчанию: 64 ожидающих запроса + один активный, ожидание в очереди 30 с,
аппаратный обмен 5 с. Ответ возвращается после оборудования или ошибки,
а не сразу с `queued`. Каждый GET делает отдельное чтение; фонового опроса,
БД и общего snapshot всех каналов нет.

Ошибки оборудования возвращаются JSON, например HTTP 504:

```json
{"error":{"code":"DEVICE_TIMEOUT","message":"Оборудование вернуло ошибку","device_status":7,"node":13,"command":"get_pressure","idx":0}}
```

- Неверный HTTP индекс/тип — 422, запрос не отправляется в порт.
- `SENSOR_UNAVAILABLE`, `BUSY`, `QUEUE_FULL` — 503.
- `DEVICE_TIMEOUT`, `HOST_TIMEOUT`, `QUEUE_TIMEOUT` — 504.
- `NOT_IMPLEMENTED`/`UNKNOWN_COMMAND` — 501; прочие аппаратные ошибки — 502.
- `DISCONNECTED` — 503; после обрыва порта сервис нужно перезапустить.

Просроченный/отменённый запрос в очереди не передаётся. Отмена HTTP-ожидания
не прерывает уже начатый физический обмен: следующий запрос ждёт его окончания.
Повторов нет. После host timeout/транспортных ошибок worker дренирует поздние
байты и ждёт секунду тишины (не дольше 3 с); при непрерывном шуме отключается.
Все POST проходят через ту же FIFO. Если ответ на управляющую команду потерян,
команда могла уже исполниться: таймаут не означает откат. Не повторяйте её
автоматически; сначала прочитайте PWM/состояние/режим. Обрыв клиента не
прерывает уже начатую команду.

## Настройка и безопасность

```powershell
.venv\Scripts\python.exe -m hub_service --serial-port COM15 --http-port 8000 --debug
```

Дополнительные параметры: `--queue-capacity`, `--queue-timeout`, `--exchange-timeout`.
`--debug` печатает TX API и все RX RAW до разбора.
Вместо `--serial-port` можно задать `MSTJUK_SERIAL_PORT`.

По умолчанию сервер слушает только localhost. Для доступа по сети:

```powershell
.venv\Scripts\python.exe -m hub_service --serial-port COM15 --host 0.0.0.0
```

User/Admin и префикс `/api/v1/admin` обозначают назначение методов,
а не ограничение доступа. Токенов, проверки Authorization и кнопки Authorize
в Swagger нет. Старые `MSTJUK_API_TOKEN`/`MSTJUK_ADMIN_TOKEN` не используются.
При сетевом запуске **любой клиент, имеющий доступ к серверу, может управлять
вентиляторами, замками и пылесосом**. Не открывайте сервис в недоверенную сеть;
ограничивайте доступ сетью/firewall. CLI выводит предупреждение при сетевом bind.
Сервис не реализует MCP-инструменты; будущий MCP должен экспортировать только
User-методы, не административные методы и не сырой универсальный POST.
Никогда не запускайте несколько workers/экземпляров на одном COM-порту.
При запуске напрямую через uvicorn ответственность за сетевой доступ остаётся у оператора:
`MSTJUK_SERIAL_PORT` должен быть задан, `--workers 1`, без reload для рабочего стенда.

На Linux/macOS: `python3 -m venv .venv`, затем `.venv/bin/python -m pip install -r requirements.txt`
и `.venv/bin/python -m hub_service --serial-port /dev/ttyUSB0`.

## Проверки

```powershell
.venv\Scripts\python.exe -m pip install -r requirements-test.txt
.venv\Scripts\python.exe -m unittest discover -s tests -v
```

Тесты проверяют HTTP, единицы измерения, User/Admin маршруты без авторизации, индексы,
ошибки, строгие аргументы, FIFO чтений/команд, переполнение/отмену/тайм-аут, shutdown/disconnect, восстановление,
CRC/resync/session wrap и 44 ранее согласованных wire-вектора. В POSIX дополнительно
проверяется полный HTTP → pyserial → виртуальный PTY-хаб → HTTP. Старые векторы дверей
с node13 сохранены для проверки байтового формата, а **новый маршрут node15** проверен
отдельными тестами. Windows COM-драйвер и реальное железо эти тесты не заменяют.
