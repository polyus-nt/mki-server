# ADR-0001: Аппаратный API с управлением на компьютере и границей User/Admin

## Status

Accepted — целевое направление утверждено пользователем 2026-10-06; реализация ещё не выполнена.

Уточнение 2026-10-07: аппаратный состав и маршрутизация замков ниже частично заменены требованиями пользователя. Актуальный перечень — два VOC, три BMP280 (давление + температура) вместо двух DS18B20, три DHT11 для влажности, два GP2Y1010AU0F для пыли, два концевика. Замки и пылесос управляются восьмилампочницей по SimpleBus через хаб, не arduino-actuator. Адрес восьмилампочницы и новый контракт ещё уточняются; см. [архитектуру](../HARDWARE-API-ARCHITECTURE.md). Решения о внешней управляющей логике и границе User/Admin остаются в силе.

## Context

Прежняя архитектура размещала PID, обработку отказов и аварийные политики на Arduino актуаторов. Агент предлагал ограниченные изменения PID/весов и не имел прямого доступа к PWM. Эти решения описаны в tjc-sketch ADR-0001, ADR-0003 и ADR-0006.

Новая задача — программный доступ к аппаратуре через простые Arduino-платы и единый API на компьютере. Сохранение прежнего контроллера на Arduino оставило бы принятие решений внутри аппаратного слоя и противоречило бы этой цели. Перенос управления на компьютер упрощает роль прошивок, но отменяет прежнюю гарантию автономного температурного регулирования при отключении компьютера.

Административные сценарии неисправностей и управление магнитным замком не должны быть доступны агенту. Альтернативой разделению интерфейсов была бы выдача MCP полного API с проверками отдельных методов, но она увеличивает область привилегий MCP.

## Decision

Arduino предоставляют только низкоуровневые операции ввода/вывода, телеметрию, транспорт и базовую проверку пакетов/аргументов. Высокоуровневые решения принимаются управляющим ПО на компьютере или агентом.

User API включает чтение температуры, VOC, концевиков, давления, PWM/RPM и установку PWM. Агенту разрешена прямая установка PWM через User API. Admin API дополнительно предоставляет чтение/установку режимов тестирования неисправностей и управление магнитным замком. MCP получает только UserApi и не экспортирует административные tools, включая get_mode; админка получает полный интерфейс.

Центральная плата маршрутизирует запросы через два Arduino-шлюза. SimpleBus связывает платы внутри МС-ТЮК; AustereMaster protocol связывает каждый шлюз с его Arduino. Транспорт между ПК и центральной платой определяется отдельно.

Аппаратный состав целевой системы: два DS18B20, два VOC (модель ещё не выбрана), два концевика для двух разных дверей, три BMP280, шесть вентиляторов с PWM/RPM и два магнитных замка, по одному на дверь. get_door_state возвращает true для закрытой двери и false для открытой. Индексы двери, концевика и замка совпадают.

Режим неисправности задаётся через `set_mode(mode, idx)` и исполняется на arduino-actuator. Одновременно активен только один сценарий на одном выбранном вентиляторе; прежнее решение о независимых режимах заменено этим ограничением. Административный `get_mode()` возвращает `{mode, idx}`, при mode=0 idx=null. Периодический режим меняет PWM сразу при включении и затем раз в 30 секунд; поступивший set_pwm применяется сразу и действует до следующего случайного обновления, не сбрасывая таймер. Повторное включение того же активного сценария также не сбрасывает таймер. Второй режим искажает только поступающие команды. Оба режима выбирают равномерное случайное целое 0..255. `get_pwm` возвращает применённое значение. При возврате в нормальный режим последнее применённое значение сохраняется до новой команды; восстановления прежнего запрошенного PWM нет.

## Consequences

Установка другого режима или выбор другого вентилятора отключает прежний сценарий перед включением нового, сохраняя последний PWM прежнего вентилятора. Явное промежуточное выключение не требуется.

Прошивки становятся аппаратными адаптерами, а управляющий алгоритм можно изменять на компьютере. Агент получает прямое воздействие на вентиляторы, но не административные функции или управление замком.

При потере связи или остановке управляющего ПО в нормальном режиме и режиме искажения поступающих команд удерживается последний применённый PWM. Периодический режим неисправности продолжает менять PWM на arduino-actuator без компьютера и шлюза. Это тестовое воздействие, а не автономное температурное регулирование. После включения/перезапуска все PWM=0 и mode=0, без восстановления из EEPROM; оба замка разблокированы. При потере связи без перезапуска замки сохраняют последнее установленное состояние. Алгоритм управления на компьютере и роль агента требуют отдельных решений.

Для целевой архитектуры эта запись заменяет направление прежних [ADR-0001](../../../tjc-sketch/docs/adr/ADR-0001-local-control-on-actuator.md) и [ADR-0003](../../../tjc-sketch/docs/adr/ADR-0003-agent-control-boundaries.md). Прежний механизм кандидатных PID/весов из [ADR-0006](../../../tjc-sketch/docs/adr/ADR-0006-candidate-control-config.md) не переносится автоматически. Исторические документы остаются без изменения.

Спецификация старого протокола и текущие прошивки пока отражают прежнюю реализацию. Детальный целевой контракт и нерешённые вопросы находятся в [HARDWARE-API-ARCHITECTURE.md](../HARDWARE-API-ARCHITECTURE.md).
