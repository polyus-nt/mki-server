# API фаблаб-теплицы: руководство пользователя

Это описание HTTP API сервиса МС-ТЮК Hub API версии `0.1.0`.
Сервис позволяет читать датчики, управлять шестью вентиляторами, двумя магнитными
замками и одним пылесосом. Теплица-химреактор реализована
[отдельным проектом](../chem-reactor-теплица/README.md) со своим сервисом и API.

Примеры ответов ниже иллюстративные: это не результаты измерений на стенде.
Источник точного списка маршрутов и схем текущего запущенного сервиса —
`GET /openapi.json`. Интерактивная документация находится по адресу `/docs`,
документация для чтения в браузере — `/redoc`.

## 1. Как подключиться

Адрес по умолчанию: `http://127.0.0.1:8000`.
Во всех примерах пути начинаются с `/`; их нужно добавлять к адресу сервера.
Индексы начинаются с **нуля**. Например, вентилятор `1` — второй вентилятор.

Чтение выполняется через `GET`, управление — через `POST` с JSON-телом
и заголовком `Content-Type: application/json`. Успешные прикладные запросы
возвращают HTTP `200` и JSON. Для POST поля обязательны; лишние поля запрещены.

Токены, пароли и заголовок `Authorization` не нужны. User/Admin — группы методов
по назначению, **не проверка прав доступа**. Любой клиент, который может
подключиться к серверу, может вызвать и административные команды.
Не публикуйте этот сервис в недоверенную сеть без внешнего ограничения доступа.
Будущий MCP-интерфейс должен предоставлять только User API; сейчас сам сервис
не реализует MCP.

### Запуск сервера на Windows

В корне репозитория на ветке `feat/fastapi-hub-service`, с Python 3.10+:

```powershell
py -3 -m venv .venv
.venv\Scripts\python.exe -m pip install -r requirements.txt
.venv\Scripts\python.exe -m hub_service --serial-port COM15
```

Укажите свой порт USB-интерфейса МС-ТЮК, не USB-порт Arduino.
Используйте рабочие прошивки Hardware API v2. Тестовая прошивка `hub-test`
для этого API не подходит. Порт должен принадлежать только сервису:
закройте все другие serial-консоли. Нельзя запускать несколько экземпляров
или несколько workers на одном порту.

Для клиента с другого компьютера оператор запускает сервис с `--host 0.0.0.0`
и ограничивает доступ firewall. Клиент использует IP компьютера сервера,
например `http://192.168.1.10:8000`, а не `0.0.0.0`.

## 2. Полный список методов

В таблице указаны полные HTTP-пути. Названия функций — логические названия
аппаратного API, а не отдельные HTTP-маршруты.

| `get_temp(idx)` | GET `/api/v1/temperature/{idx}` | `0..2` | Температура BMP280 |
| `get_pressure(idx)` | GET `/api/v1/pressure/{idx}` | `0..2` | Давление BMP280 |
| `get_voc(idx)` | GET `/api/v1/voc/{idx}` | `0..1` | VOC Index SGP40 |
| `get_humidity(idx)` | GET `/api/v1/humidity/{idx}` | `0..2` | Влажность DHT11 |
| `get_dust()` | GET `/api/v1/dust` | Без индекса | ADC и напряжение датчика пыли |
| `get_door_state(idx)` | GET `/api/v1/doors/{idx}/state` | `0..1` | Состояние концевика двери |
| `get_pwm(idx)` | GET `/api/v1/fans/{idx}/pwm` | `0..5` | Применённый PWM |
| `get_rpm(idx)` | GET `/api/v1/fans/{idx}/rpm` | `0..5` | Измеренная скорость вентилятора |

## 3. Чтение датчиков

### Температура, давление, VOC и влажность

Эти четыре вида показаний имеют одинаковую структуру ответа:

```json
{
  "idx": 0,
  "value": 100653,
  "unit": "Pa",
  "valid": true,
  "fresh": true,
  "age_ms": 123,
  "received_at": "2026-10-10T00:00:00Z"
}
```

| Поле | Что означает |
| --- | --- |
| `idx` | Индекс запрошенного датчика |
| `value` | Числовое значение в единицах `unit` |
| `unit` | Строковое обозначение единицы, см. таблицу ниже |
| `valid` | Есть корректное измерение; успешный ответ текущего сервиса содержит `true` |
| `fresh` | Новое успешное измерение ещё не было выдано через интерфейс чтения платы |
| `age_ms` | Возраст измерения на Arduino в миллисекундах |
| `received_at` | Время получения ответа сервером, UTC; не время физического измерения |

| Датчик | `unit` | Интерпретация |
| --- | --- | --- |
| BMP280, температура | `degC` | Градусы Цельсия, например `23.45`; idx соответствует BMP280 с тем же индексом давления |
| BMP280, давление | `Pa` | Паскали, целое число; для гПа разделите на 100 |
| SGP40 | `VOC Index` | Индекс `1..500`; не ppm и не концентрация газа |
| DHT11 | `%RH` | Относительная влажность `0..100`, например `55.5` |

Вызов GET читает кэш на Arduino, а не запускает немедленное новое измерение.
Сами датчики обновляются прошивкой независимо от HTTP-клиента.

`fresh=false` не является ошибкой: повторный запрос до обновления датчика
возвращает прежнее измерение. `fresh=true` не означает изменения числа и
не гарантирует малого возраста. Флаг общий для всех клиентов, включая Arduino
TEST-консоль: чтение одним клиентом может сбросить его для следующего.
У BMP280 свежесть температуры и давления учитывается отдельно.

Для контроля давности используйте `age_ms`, выбирая допустимый возраст под
свою задачу. Значение ограничено `65534`: при достижении этого предела
показание может быть старше 65.534 секунды. Если новое чтение датчика не удалось,
прошивка может сохранить старое корректное значение с `fresh=false` и растущим
возрастом. Поэтому `valid=true` само по себе не подтверждает, что датчик
продолжает успешно обновляться. Если корректных данных нет, возвращается ошибка,
а не фиктивное значение или успешный ответ с `valid=false`.

### Пыль: GP2Y1010AU0F

Единственный GP2Y1010AU0F: сигнал A1, LED A2.
`GET /api/v1/dust` (без индекса в адресе и JSON):

```json
{
  "adc": 205,
  "voltage_mv": 1002,
  "voltage_v": 1.002,
  "valid": true,
  "fresh": false,
  "age_ms": 800,
  "received_at": "2026-10-10T00:00:00Z"
}
```

`adc` — сырой отсчёт `0..1023`; `voltage_mv` — рассчитанное напряжение в
милливольтах, `voltage_v` — то же значение в вольтах. Расчёт прошивки использует
опорное напряжение 5 В. Концентрация пыли не выдаётся: для неё нужна калибровка.
Поля качества имеют тот же смысл, что у остальных датчиков.

## 4. Двери и магнитные замки

### Состояние двери

`GET /api/v1/doors/0/state`:

```json
{"idx":0,"closed":true,"received_at":"2026-10-10T00:00:00Z"}
```

`closed=true` — концевик активен: вход кнопочницы замкнут на GND (LOW),
что в текущей конфигурации трактуется как закрытая дверь.
`false` — концевик не активен. Соответствие физическому состоянию двери
необходимо проверить после монтажа. Индексы `0/1` — два отдельных концевика.

### Управление замком

`POST /api/v1/admin/locks/0`:

```json
{"lock_state":true}
```

`true` включает блокировку выбранного замка; `false` отключает.
Два замка управляются независимо: idx `0` — выход 1 lmp, idx `1` — выход 2.
В текущей схеме LOW блокирует, HIGH разблокирует. При запуске платы выходы
установлены в LOW: оба замка заблокированы (`lock_state=true`).
Кнопка 3 на кнопочнице открывает замок 0, кнопка 4 — замок 1 на 2 секунды.
Таймер исполняется на lmp без компьютера: повторное нажатие перезапускает его,
удержание не продлевает. Явный `set_door_lock` отменяет таймер данного замка;
`false` оставляет его разблокированным до следующего действия.
`get_door_lock` во время импульса возвращает false. Концевики по-прежнему
показывают физическое положение двери; стартовая блокировка не подменяет их.
Кнопочные команды не добавляют HTTP/MCP эндпоинтов.

Ответ на команду:

```json
{"acknowledged":true,"received_at":"2026-10-10T00:00:00Z"}
```

Это подтверждение выполнения команды платой, не доказательство физического
срабатывания магнитного замка.

`GET /api/v1/locks/0/state`:

```json
{"idx":0,"lock_output_enabled":true,"received_at":"2026-10-10T00:00:00Z"}
```

`lock_output_enabled` отражает состояние управляющего выхода блокировки,
**не уровень HIGH**, не состояние концевика и не физическое удержание двери.
Открыта ли дверь, читайте отдельно через `/doors/{idx}/state`.

## 5. Вентиляторы

Индексы `0..5` едины для всего API. Физически вентиляторы `0..3` обслуживает
первая Arduino через шлюз 14, `4..5` — вторая Arduino через шлюз 17.
Клиенту не нужно знать локальные индексы или адреса плат.

### PWM: чтение и установка

`GET /api/v1/fans/2/pwm`:

```json
{"idx":2,"value":100,"unit":"PWM 0..255","received_at":"2026-10-10T00:00:00Z"}
```

`POST /api/v1/fans/2/pwm` с телом:

```json
{"pwm":100}
```

возвращает ответ той же структуры. `value` — **применённое** значение PWM,
не обязательно запрошенное: в режиме неисправности 2 запрос `100` может
дать ответ `230`. GET тоже возвращает применённое значение.
Это значение, установленное прошивкой на выходе, не электрическое измерение
PWM отдельным датчиком и не скорость вращения.

PWM задаётся целым числом `0..255`, не процентами. `0` выключает реле питания
вентилятора; любое ненулевое значение включает реле и устанавливает PWM.
Запросы `"100"`, `100.5`, `true`, отрицательные числа и числа больше 255
не принимаются.

### Обороты

`GET /api/v1/fans/2/rpm`:

```json
{"idx":2,"value":1200,"unit":"rpm","received_at":"2026-10-10T00:00:00Z"}
```

Это измеренные обороты в минуту по тахосигналу. Прошивка рассчитывает их
примерно раз в секунду; немедленное чтение после изменения PWM ещё может
показать прежнее значение. Нулевые RPM сами по себе не доказывают неисправность:
вентилятор может быть выключен или ещё не раскрутился.

При старте Arduino PWM равен 0, реле выключены. При потере связи удерживается
последний применённый PWM; автоматической остановки нет.

## 6. Пылесос

Пылесос один, поэтому индекс не используется. Его выход — пин 3 lmp:
HIGH включает, LOW выключает. При старте платы он выключен.

`POST /api/v1/admin/vacuum`:

```json
{"mode":1}
```

`mode=1` включает, `mode=0` выключает. Это целое число, не boolean.
Ответ — `{"acknowledged":true,"received_at":"..."}`.

`GET /api/v1/vacuum/state`:

```json
{"enabled":true,"received_at":"2026-10-10T00:00:00Z"}
```

`enabled` — состояние управляющего выхода, а не подтверждение вращения
двигателя или работы всасывания.

## 7. Административные режимы неисправности

Одновременно допускается только один сценарий для одного вентилятора
из всех шести. Это реальные изменения управления аппаратурой,
а не подмена RPM-телеметрии.

`GET /api/v1/admin/mode`:

```json
{"mode":2,"idx":4,"received_at":"2026-10-10T00:00:00Z"}
```

В нормальном режиме ответ содержит `"mode":0,"idx":null`.

`POST /api/v1/admin/mode`:

```json
{"mode":2,"idx":4}
```

| `mode` | Поведение выбранного вентилятора |
| --- | --- |
| `0` | Сценарий выключен; сохраняется последний применённый PWM |
| `1` | Сразу устанавливается случайный физический PWM, затем меняется каждые 30 секунд независимо от поступления команд |
| `2` | Только поступающие `set_pwm` заменяются случайным физическим PWM; само включение режима выход не меняет |

В mode 1 обычная команда PWM применяется как передана, но следующий
периодический тик снова заменит её случайным значением.
В mode 2 последнее применённое значение сохраняется до новой команды.
Другие вентиляторы управляются штатно.

Для отключения сценария отправьте, например, `{"mode":0,"idx":0}`.
Поле `idx` обязательно и должно быть `0..5` даже при mode 0, хотя в этом случае
оно игнорируется. Значение `null` в запросе не принимается.
После отключения **нет восстановления ранее запрошенного PWM**:
если фактически было установлено 230, останется 230 до новой команды.

При смене режима или вентилятора хаб сначала отключает предыдущий сценарий,
затем включает новый. Старый вентилятор сохраняет последнее значение PWM.
Повтор установки того же режима для того же вентилятора не перезапускает
сценарий и не вызывает немедленную повторную рандомизацию.

Для чтения и изменения глобального режима нужны обе actuator Arduino:
хаб проверяет их состояния. Обычные PWM/RPM-запросы к работающей плате
не требуют доступности второй. Смена режима — многошаговая операция;
при ошибке не предполагайте, что прежний режим сохранился, проверяйте `get_mode`.
При потере связи mode 1 продолжает периодическую работу на Arduino.

## 8. Диагностика сервиса и хаба

`GET /health` не опрашивает железо и доступен во время аппаратного обмена:

```json
{
  "status":"ready",
  "serial_open":true,
  "queue_depth":0,
  "queue_capacity":64,
  "active":false,
  "recovering":false,
  "last_response_at":null
}
```

`queue_depth` — количество ожидающих запросов, без активного.
`active` — worker обрабатывает запрос; `recovering` — восстанавливает тишину
на шине после транспортной ошибки. `last_response_at` — время последнего
принятого ответа, включая аппаратные ответы с ошибкой; до первого ответа — null.
`ready` и HTTP 200 означают, что сервис считает порт доступным, **не** что
все платы и датчики работают. При отключении возвращается HTTP 503,
`status="disconnected"`, `serial_open=false`.

`GET /api/v1/hub/probe` проверяет только связь с хабом, без нижних плат:

```json
{"responding":true,"expected_status":"INVALID_INDEX","received_at":"2026-10-10T00:00:00Z"}
```

`INVALID_INDEX` здесь ожидаем: сервис специально посылает индекс,
который хаб должен отклонить. В этом диагностическом маршруте это успех.

`GET /api/v1/capabilities` возвращает конфигурацию: `greenhouse="fablab"`,
`protocol_version=2`, каналы `channels` с count/node/command, отдельный `vacuum`,
маршруты вентиляторов `actuator_routes`, `admin_enabled=true`,
`authentication="none"`, `access="user-and-admin"`,
`chemreactor="not_implemented"`. Это описание поддерживаемой конфигурации,
не автоматическое обнаружение подключённого оборудования.

## 9. Очередь, время ожидания и повторные запросы

Все аппаратные GET и POST попадают в одну FIFO-очередь. Одновременно
выполняется один обмен. HTTP-запрос ждёт своей очереди и возвращает конечный
ответ или ошибку; отдельного ответа `queued`, job ID и polling API нет.
Служебные `/health`, `/capabilities` и страницы документации порт не занимают.

По умолчанию допускаются 64 ожидающих запроса плюс один активный.
Ожидание до начала обмена — максимум 30 секунд, обмен с аппаратурой — 5 секунд.
После некоторых ошибок перед следующим обменом выполняется восстановление
шины: ожидание секунды тишины, максимум 3 секунды.
Настройки оператора: `--queue-capacity`, `--queue-timeout`, `--exchange-timeout`.
Для клиента рекомендуется таймаут 45 секунд при стандартных настройках.

Каждый GET — отдельный запрос к плате; объединения одинаковых запросов,
фонового HTTP-опроса, БД и согласованного снимка всех каналов нет.
Результаты нескольких GET могут относиться к разным моментам времени.
Для регулярного опроса отправляйте запросы последовательно или ограничивайте
параллелизм, чтобы не заполнять очередь быстрее, чем она обслуживается.

Просроченный в очереди запрос не отправляется в аппаратуру. Отмена ожидания
клиентом не прерывает уже начатый обмен. Автоматических повторов нет.
**Таймаут POST не означает откат или отсутствие исполнения команды.**
Сначала прочитайте соответствующие PWM, режим или состояние выхода,
затем решайте, нужна ли новая команда. Потеря HTTP/COM-связи сама по себе
не является командой отключения аппаратуры.

## 10. Ошибки

Ошибки аппаратуры и очереди имеют формат:

```json
{
  "error": {
    "code":"DEVICE_TIMEOUT",
    "message":"Оборудование вернуло ошибку",
    "device_status":7,
    "node":13,
    "command":"get_pressure",
    "idx":0
  }
}
```

Гарантированная основа — `error.code` и `error.message`.
Дополнительные поля зависят от ошибки: `device_status`, `node`, `command`,
`idx`, а у `HOST_TIMEOUT` также `rx_bytes`. Для программной обработки
используйте `code`, а не русскоязычный текст сообщения.

| HTTP | `code` | Значение |
| --- | --- | --- |
| 422 | `INVALID_INDEX`, `INVALID_ARGUMENT` | Аппаратура отклонила индекс или аргумент |
| 501 | `UNKNOWN_COMMAND`, `NOT_IMPLEMENTED` | Команда неизвестна или ещё не реализована |
| 503 | `SENSOR_UNAVAILABLE` | Нет доступного корректного измерения; возможен прогрев датчика |
| 503 | `BUSY` | Аппаратный узел занят |
| 503 | `QUEUE_FULL` | Серверная очередь заполнена |
| 503 | `DISCONNECTED` | Порт/worker недоступен; после обрыва порта перезапустите сервис |
| 503 | `SHUTTING_DOWN` | Сервис останавливается |
| 504 | `QUEUE_TIMEOUT` | Истекло ожидание в очереди, запрос не отправлен |
| 504 | `HOST_TIMEOUT` | Сервер не получил подходящий ответ хаба вовремя |
| 504 | `DEVICE_TIMEOUT` | Хаб/шлюз не дождался нижнего узла |
| 502 | `UNSUPPORTED_VERSION` | Несовместимая версия аппаратного протокола |
| 502 | `INTERNAL_ERROR` | Аппаратная внутренняя ошибка |
| 502 | `REQUEST_ID_CONFLICT` | Конфликт внутренней идентификации аппаратного запроса |
| 502 | `INVALID_NODE` | Недопустимый аппаратный узел |
| 502 | `TRANSPORT_OVERFLOW` | Переполнение аппаратного транспорта |
| 500 | `INTERNAL_ERROR` | Внутренняя ошибка worker сервера |

HTTP-валидация выполняется **до передачи на плату**. Неверный индекс,
отсутствующее поле, лишнее поле или неверный тип дают HTTP 422 с другой
структурой — стандартным массивом `detail` FastAPI, например:

```json
{"detail":[{"type":"int_type","loc":["body","pwm"],"msg":"Input should be a valid integer","input":"100"}]}
```

Также возможны стандартные HTTP 404 (неверный путь) и 405 (неверный метод).
Проверяйте HTTP-статус перед использованием измерения.

## 11. Примеры работы на Windows

### PowerShell

```powershell
$apiBase = "http://127.0.0.1:8000"
Invoke-RestMethod "$apiBase/api/v1/temperature/0"
Invoke-RestMethod "$apiBase/api/v1/pressure/0"
Invoke-RestMethod "$apiBase/api/v1/fans/4/rpm"

# Эти команды действительно управляют аппаратурой.
Invoke-RestMethod "$apiBase/api/v1/fans/4/pwm" -Method Post `
  -ContentType "application/json" -Body '{"pwm":100}'
Invoke-RestMethod "$apiBase/api/v1/admin/locks/0" -Method Post `
  -ContentType "application/json" -Body '{"lock_state":true}'
Invoke-RestMethod "$apiBase/api/v1/admin/vacuum" -Method Post `
  -ContentType "application/json" -Body '{"mode":1}'

# Включение сценария неисправности и последующее отключение.
Invoke-RestMethod "$apiBase/api/v1/admin/mode" -Method Post `
  -ContentType "application/json" -Body '{"mode":2,"idx":4}'
Invoke-RestMethod "$apiBase/api/v1/admin/mode"
Invoke-RestMethod "$apiBase/api/v1/admin/mode" -Method Post `
  -ContentType "application/json" -Body '{"mode":0,"idx":4}'
```

### Человекочитаемая консоль

Пока сервер запущен, откройте другой терминал в корне репозитория:

```powershell
py -3 scripts/api_console.py
```

Клиент использует только стандартную библиотеку Python и общается по HTTP.
Примеры вводимых команд:

```text
health
capabilities
probe
temp 0
pressure 2
voc 1
humidity 0
dust
door 0
pwm 4
rpm 4
lock 0
vacuum
get_mode
set_pwm 4 100
set_mode 2 4
set_mode 0 4
set_door_lock 0 1
set_door_lock 0 0
set_vacuum 1
set_vacuum 0
selftest
help
exit
```

Для чтений также доступны полные названия `get_temp`, `get_pressure`,
`get_voc`, `get_humidity`, `get_dust`, `get_door_state`, `get_pwm`, `get_rpm`,
`get_door_lock`, `get_vacuum`. В консоли состояния замка и пылесоса вводятся
как `0/1`; клиент сам преобразует замок в JSON boolean.

Однократная команда и подключение по сети:

```powershell
py -3 scripts/api_console.py --command "temp 0"
py -3 scripts/api_console.py --command selftest
py -3 scripts/api_console.py --url http://192.168.1.10:8000 --timeout 45
```

`selftest` получает `/openapi.json` и последовательно вызывает все прикладные
GET-маршруты из схемы со всеми допустимыми индексами: сейчас 34 запроса
плюс получение схемы. Продолжает после ошибок. Не вызывает POST,
не переключает выходы, не повторяет запросы. `fresh=false` допускается.
Это проверка доступности, не калибровки датчиков и не физической работы механизмов.
Чтения selftest могут сбрасывать `fresh`, как и любые другие чтения.
Коды выхода: 0 — успех, 1 — ошибка проверки/запроса, 2 — неверная команда,
130 — прерывание пользователем.

## 12. Рекомендуемая проверка стенда

1. Запустите сервис и убедитесь, что `/health` возвращает `ready`.
2. Вызовите `/api/v1/hub/probe`: это проверит обмен с центральной платой.
3. Выполните `selftest`: он покажет, какие нижние узлы или каналы недоступны.
4. Проверьте возрастающую/обновляющуюся телеметрию, а не только HTTP 200.
5. Управляющие команды проверяйте отдельно, под наблюдением оператора:
   подтвердите PWM чтением и RPM, работу замка — физически и концевиком,
   работу пылесоса — физически. `selftest` этого не делает.

## Общая шина и задержка запросов

Хаб автономно опрашивает кнопки открытия, даже без FastAPI.
Перед каждым аппаратным запросом сервис ждёт секунду тишины на общей
полудуплексной шине (не более 3 с); хаб оставляет 1.5 с между опросами.
Это ожидание предшествует exchange-timeout и добавляет задержку HTTP-вызову.
FIFO и единственный владелец COM-порта сохраняются. Используйте обновлённый
сервис и sensor_console: старый клиент без ожидания тишины может столкнуться
с автономным обменом. Дополнительные инициаторы на шине не допускаются.
