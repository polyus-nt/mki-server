# Аппаратный протокол МС-ТЮК v2

Статус: экспериментальный контракт реализован в feature-ветках Arduino,
Arduino-шлюзов, центрального хаба и Rust-приложения. Сборки и автоматические
тесты не заменяют проверку на стенде. Новая система несовместима с прежней
29-байтовой телеметрией, PID/config-командами и старым GraphML.

Связанные документы: [архитектура](HARDWARE-API-ARCHITECTURE.md),
[HTML: рабочий протокол и текстовая TEST-консоль](HARDWARE-PROTOCOL.html),
[реализация](FIRMWARE-IMPLEMENTATION.md),
[JSON-контракт](protocol/hardware-v2.json),
[44 эталонных обмена](protocol/hardware-v2-vectors.json).

## Человеческим языком

Каждый вызов API становится запросом из 28 байтов. Запрос проходит через
центральный хаб и нужный Arduino-шлюз до Arduino. Ответ возвращается тем же
маршрутом, содержит тот же номер запроса и код операции. Значения передаются
числами в байтах, не строками вида `25.08`.

В Rust одна общая очередь для MCP, админки и фонового опроса. Одновременно
выполняется один физический обмен. Остальные запросы ждут своей очереди.
Ответ MCP появляется после ответа оборудования или окончательной ошибки,
а не сразу с фиктивным успехом `queued`.

## Транспорт и маршрутизация

Компьютер и шлюзы используют одну USART1/SimpleBus-линию хаба; отдельный
неподтверждённый порт компьютера не назначен. Перед запуском линии нужно
проверить электрическую совместимость и полудуплекс на стенде.

Адреса: компьютер 99 (`63`), хаб 12 (`0C`), sensors-шлюз 13 (`0D`),
actuator-шлюз 14 (`0E`). Компьютер посылает байты кадра адресу хаба,
хаб посылает их адресу нужного шлюза, шлюз отвечает хабу, хаб — компьютеру.
На общей линии хаб отличает запрос и ответ по полю kind, а не выдуманному
адресу отправителя. В SimpleBus-пакете адреса отправителя нет.

Пакет линии: `CR | ASCII hex адреса (2 символа) | один байт | LF`.
Размер — 5 байтов; 9600, 8N1. Hex только верхнего регистра.
Один кадр API — 28 таких пакетов. После отправки каждого пакета выдерживается
минимум 2 мс. Между шлюзом и Arduino используется AustereMaster,
который переносит те же 28 байтов без изменения.

## Кадр

v2 несовместим с v1. Сервер, хаб, оба шлюза и обе Arduino должны обновляться
согласованно. Автоматического fallback к старому 20-байтовому формату нет.

| Смещение | Размер | Поле |
| --- | --- | --- |
| 0 | 2 | magic A5 5A |
| 2 | 1 | version=2 |
| 3 | 1 | kind: 1 запрос, 2 ответ |
| 4 | 2 | tx_id, big-endian |
| 6 | 1 | node: 13 sensors, 14 actuator |
| 7 | 1 | command |
| 8 | 1 | status: 0 в запросе, код результата в ответе |
| 9 | 1 | idx, с нуля |
| 10 | 8 | data |
| 18 | 8 | session_id, big-endian |
| 26 | 2 | CRC-16/CCITT-FALSE, big-endian |

CRC покрывает байты 2..25; polynomial=0x1021, init=0xFFFF, refin/refout=false,
xorout=0. Проверка `123456789` даёт 0x29B1. Неиспользованные data-байты нулевые.
Повреждённый CRC/частичный кадр не применяется.

Ответ принимается только при совпадении version, kind=2, session_id, tx_id, node, command,
idx с активным запросом. Неверный статус, резервные поля, диапазоны, качество
измерения или результат set_mode не завершают ожидающий запрос.
Парсеры ограничены по памяти и восстанавливаются после шума/потери байта.

## Команды

| Команда | Код | Node | idx | Ответ при успехе | Доступ |
| --- | --- | --- | --- | --- | --- |
| get_temp | 20 | 13 | 0..2 | i32, сотые °C + качество | User |
| get_voc | 21 | 13 | 0..1 | u32, VOC Index 1..500 + качество | User |
| get_door_state | 22 | 13 | 0..1 | bool: true=закрыто | User |
| get_pressure | 23 | 13 | 0..2 | u32, Па + качество | User |
| get_humidity | 24 | 13 | 0..2 | u32, сотые %RH, 0..10000 + качество | User |
| get_dust | 25 | 13 | 0..1 | u16 ADC + u16 мВ + качество | User |
| get_pwm | 30 | 14 | 0..5 | u8, применённый PWM | User |
| get_rpm | 31 | 14 | 0..5 | u32 RPM | User |
| set_pwm | 32 | 14 | 0..5 | u8, фактически применённый PWM | User |
| get_mode | 40 | 14 | FF | mode + активный idx | Admin |
| set_mode | 41 | 14 | 0..5 | mode + активный idx | Admin |

Коды в таблице шестнадцатеричные. GET-запросы содержат восемь нулей data.
SET_PWM: data[0]=PWM 0..255; SET_MODE: data[0]=mode 0..2; остальные нули.
Результат SET_PWM может отличаться от запрошенного значения при mode=2.
GET_MODE/SET_MODE: data[0]=mode; data[1]=idx; при mode=0 idx=FF (API null),
иначе 0..5; оставшиеся шесть байтов нулевые. Только один неисправный вентилятор.

mode=0 — штатные команды; mode=1 меняет физический PWM выбранного вентилятора
сразу и затем раз в 30 с, даже при отсутствии связи; mode=2 заменяет случайным
PWM только новые SET_PWM для выбранного вентилятора. Повтор включения того же
сценария и SET_PWM не сбрасывают таймер mode=1. Смена/выключение режима не
восстанавливают ранее запрошенный PWM: удерживается последнее применённое
значение до новой команды. После перезапуска mode=0, все PWM=0.

Температура и давление — три BMP280; влажность — три DHT11; VOC — два SGP40.
VOC Index безразмерный, не ppm и не SRAW; первичный blackout алгоритма
не является валидным нулевым индексом. GP2Y1010AU0F возвращает ADC 0..1023 и напряжение: data[0..1]=u16 ADC,
data[2..3]=u16 мВ; quality/age остаются на позициях 4..7. Концентрация пыли не вычисляется.
Измерение каждого датчика раз в секунду: LOW, 280 мкс, analogRead, 40 мкс, HIGH.
Сам analogRead добавляет время выполнения к импульсу. Для перевода используется
API_DUST_REFERENCE_MV (по умолчанию 5000); оно должно соответствовать реальному
опорному напряжению ADC. Arduino API не может доказать подключение аналогового датчика.
Без настроенной распиновки датчик возвращает NOT_IMPLEMENTED;
до первого успешного результата — SENSOR_UNAVAILABLE.

Два магнитных замка и пылесос принадлежат восьмилампочнице.
Её адрес/команды пока не согласованы: сервер не назначает маршрут.
0x42 не поддерживается Arduino; оба endpoint возвращают UNKNOWN_COMMAND.

### Качество измерения

Data: [0..3] число big-endian; [4] flags (valid=1, fresh=2);
[5..6] age_ms; [7]=0. Успешный ответ допускает flags=1 или 3,
возраст 0..65534 мс, с насыщением на верхней границе.
fresh означает новое ещё не выданное измерение, не «возраст равен нулю».
При ошибке датчика сохранённый результат остаётся валидным, fresh=0,
его возраст растёт. Сохранённый ответ в GUI дополнительно содержит время
получения: возраст кэша компьютера не следует путать с возрастом датчика.

Примеры data: 25.08 °C — `00 00 09 CC 03 00 00 00`;
100653 Па — `00 01 89 2D 03 00 00 00`;
VOC Index 100 — `00 00 00 64 03 00 00 00`;
55.5 %RH — `00 00 15 AE 03 00 00 00`.
В MCP температура/влажность преобразуются в обычные числа с единицами,
давление остаётся в Па. RPM — полный u32, без старой нормализации.

## Ошибки

Коды 0..12: OK, INVALID_INDEX, INVALID_ARGUMENT, UNKNOWN_COMMAND,
NOT_IMPLEMENTED, SENSOR_UNAVAILABLE, BUSY, DEVICE_TIMEOUT,
UNSUPPORTED_VERSION, INTERNAL_ERROR, REQUEST_ID_CONFLICT, INVALID_NODE,
TRANSPORT_OVERFLOW. При ошибке все восемь data-байтов нулевые.

Сервер отдельно возвращает отказ в постановке, QUEUE_TIMEOUT, HOST_TIMEOUT,
DISCONNECTED. Потерянный ответ управляющей команды означает
`outcome: unknown`: команда могла физически выполниться.
Отклонённый/просроченный запрос, не начавший отправку, имеет `not_sent`.
Никакие управляющие запросы автоматически не повторяются.

## Очередь, идентификаторы и тайм-ауты

Один worker владеет COM-портом, включая чтение, запись и pacing;
GUI не исполняет I/O. Общая FIFO — максимум 64 ожидающих запроса плюс один
активный. Фоновый опрос добавляет запрос только при отсутствии ожидающих
и активного; при отключении не создаёт очередь. Полный цикл всех каналов
не является одновременным снимком аппаратуры.

Ожидание в очереди ограничено 30 с, физический обмен — отдельно 5 с.
Шлюз ждёт до 1.5 с, хаб — до 3 с. arduino_execution=500 мс в JSON —
проектный бюджет, не дополнительный реализованный таймер Arduino. Частичный кадр сбрасывается при
паузе 250 мс или общей длительности 1000 мс. После открытия/host timeout или ошибки транспорта 7/9/12
компьютер дренирует старые байты и ждёт 1 с тишины; шум может продлить ожидание,
но общий предел 3 с приводит к явному отключению и завершению очереди.
Хаб использует quiet 250 мс с пределом recovery 1000 мс.
При ошибке/закрытии порта все активные и ожидающие клиенты получают результат.

decision_id — идентификатор решения клиента, не аппаратный tx_id.
Одинаковые decision_id и аргументы ожидают тот же окончательный результат;
повтор после завершения получает сохранённый результат, без новой отправки.
Тот же decision_id с другими аргументами отклоняется как конфликт.
В памяти хранится до 4096 завершённых решений плюс ограниченное число активных.
Результаты сохраняются в SQLite hardware_decisions_v2 и доступны после вытеснения
из кэша и перезапуска. До постановки decision_id и аргументы записываются на диск.
Если прошлый процесс остановился без финальной записи, повтор этого ID отклоняется
как неизвестный исход: проверяем оборудование, а не повторяем воздействие.
При ошибке записи БД новая команда не принимается; ошибка сохранения результата
не создаёт автоматического повтора. Удаление файла БД лишает этой защиты.
id — 1..128 байтов, до 64 ожидателей на одно решение.
Запрос без decision_id не идемпотентен; для MCP SET_PWM ID обязателен.

tx_id 1..65535 — номер ВНУТРИ сессии, не ограничение срока работы.
При старте процесса создаётся случайная ненулевая 64-битная session_id.
После 65535 сервер увеличивает session_id (пропускает 0), продолжает с tx_id=1
и не останавливает очередь или опрос. Каждому ожидающему запросу назначена
собственная пара session_id/tx_id; смена сессии не меняет уже принятые запросы.
Хаб и шлюзы пересылают session_id, Arduino копирует её в ответ. Ответ старой
сессии с совпадающим номером не завершает новый запрос.
Случайная сессия практически исключает совпадение между запусками, но не является
математической глобальной уникальностью или аутентификацией. Корреляция не
обещает exactly-once при сбое питания: для этого используется журнал решений
с отказом от повторного исполнения неопределённых команд.

Отмена HTTP-ожидания не отменяет уже принятый аппаратный запрос. Клиент может
повторить тот же decision_id с теми же аргументами и получить его результат.

## Граница MCP/Admin

MCP получает только объект UserApi. Административные get_mode/set_mode не
регистрируются как tools и дополнительно отклоняются самим UserApi.
Локальная GUI-админка ставит административные команды в ту же FIFO.
MCP слушает только 127.0.0.1:8765 и требует bearer token.
По умолчанию PWM через MCP запрещён; TJC_AGENT_PHASE=full разрешает его.
Старые стадии weights/pid и PID/config/emergency tools удалены.

## Проверка

`python3 scripts/validate_hardware_protocol.py` проверяет JSON, поля, CRC,
44 обмена, негативные кадры и оболочки. Векторы — эталоны контракта,
не доказательство физической работоспособности датчиков.
Rust тестирует эти же байты и декодированные API-результаты; native C++
прогоняет неизменный кадр через Hub → шлюз → Arduino.
