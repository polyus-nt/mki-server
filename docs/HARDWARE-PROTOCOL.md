# Аппаратный протокол МС-ТЮК — проект v1

**Требует пересмотра после уточнения оборудования 2026-10-07.** Актуальный состав записан в [архитектуре](HARDWARE-API-ARCHITECTURE.md): три BMP280 дают давление и температуру вместо DS18B20, добавлены три DHT11 для влажности и два GP2Y1010AU0F для пыли; замки и пылесос управляются восьмилампочницей, подключённой к хабу по SimpleBus. Ниже и в JSON сохранён прежний проект: get_temp 0..1, маршрут замков через node=14 и отсутствие новых команд пока не исправлены, чтобы не назначать неподтверждённые адреса и API. Его векторы проверяют прежнее кодирование, а не актуальный аппаратный контракт. Реализацию по этому проекту начинать нельзя до согласования изменений.

Статус: спецификация для шага 1. Прикладные правила из архитектуры сохранены. Фиксированный кадр с CRC, числовые единицы и возврат применённого PWM из set_pwm предложены пользователю; до ответа это варианты проекта, а не дополнительные утверждённые требования. Прошивки и приложение ещё используют прежний протокол.

Связанные файлы: [архитектура](HARDWARE-API-ARCHITECTURE.md), [машиночитаемый контракт](protocol/hardware-v1.json), [общие векторы](protocol/hardware-v1-vectors.json). Целевой набор операций — семь User API и три Admin API. Новых публичных методов эта спецификация не добавляет.

## Коротко, человеческим языком

Компьютер отправляет одну команду и ждёт один ответ. Хаб выбирает нужный шлюз, шлюз передаёт команду своей Arduino, Arduino читает вход или устанавливает выход. Ответ возвращается тем же путём. Хаб и шлюзы не принимают решений о температуре, дверях или требуемой скорости вентилятора.

Каждая команда содержит адрес узла, название операции в виде числового кода, индекс устройства и аргумент, если он нужен. Номер запроса связывает ответ с командой. Контрольная сумма позволяет обнаружить повреждённое сообщение. В ответе обязательно есть либо результат, либо код ошибки: отсутствие датчика не выдаётся за показание ноль.

Примеры на уровне API (индексы начинаются с нуля):

- `get_temp(1)` читает второй датчик температуры через шлюз датчиков. Ответ может быть 25.5 °C с возрастом измерения; Arduino не ждёт нового преобразования.
- `set_pwm(2, 100)` управляет третьим вентилятором через шлюз актуаторов. В обычном режиме применяется 100. В режиме 2 команда может применить 230: ответ и последующий `get_pwm(2)` сообщают именно 230.
- `set_mode(1, 2)` из админки сразу случайно меняет PWM третьего вентилятора и повторяет это каждые 30 секунд, даже без компьютера. `set_mode(2, 2)` меняет только новые команды PWM этому вентилятору.
- `set_mode(0, 2)` выключает единственный сценарий, но не возвращает старый PWM. Выход удерживает последнее значение до новой команды.
- `set_door_lock(1, true)` блокирует вторую дверь. Этот метод и методы режима доступны только админке, не агенту.

Если ответ на меняющую команду потерялся, компьютер не повторяет её автоматически: команда могла уже сработать. Если связь пропала, Arduino сохраняет выходы, а периодический режим продолжает работать.

## Участники и транспорт

| Участник | ID, десятичный | ASCII hex для SimpleBus |
| --- | ---: | --- |
| Компьютер | 99 | 63 |
| Центральная плата / хаб | 12 | 0C |
| Шлюз датчиков | 13 | 0D |
| Шлюз актуаторов | 14 | 0E |

В кадре node обозначает конечный узел: 13 — Arduino датчиков через её шлюз, 14 — Arduino актуаторов через её шлюз. Arduino не требуется собственный SimpleBus-адрес.

Внешний интерфейс ПК ↔ хаб предлагается сохранить последовательным, 9600 бод, 8N1, с совместимой с существующим приложением обёрткой одного байта `CR | AA | D | LF`. Запросы ПК адресуются хабу 12, ответы хаба — ПК 99. Это внешний интерфейс компьютера; внутрисистемная связь хаба со шлюзами остаётся SimpleBus. Его совпадающее пятибайтовое представление позволяет использовать существующий последовательный адаптер.

Хаб передаёт кадр на шлюз, указанный node; шлюз отвечает хабу 12. Между шлюзом и Arduino байты того же прикладного кадра передаются через существующие ArduinoAdapter/arduino_link и AustereSerialMaster. Обёртка SimpleBus через этот участок не передаётся.

Хаб и шлюз буферизуют и проверяют полный кадр перед его пересылкой. Запрос доходит до Arduino без изменения tx_id/node/command/idx/data. Ответ доходит до ПК без изменения полей. Единственное исключение — транспортный посредник может создать собственный ответ об ошибке, когда запрос не удалось доставить или ответ не пришёл; он использует реквизиты принятого запроса.

## Прикладной кадр

Запрос и ответ имеют одинаковую длину **20 байтов**. Многобайтные числа — big-endian. Размер payload не передаётся и не зависит от значения байтов.

| Смещение | Длина | Поле | Значение |
| ---: | ---: | --- | --- |
| 0 | 2 | magic | A5 5A |
| 2 | 1 | version | 01 |
| 3 | 1 | kind | 01 запрос, 02 ответ |
| 4 | 2 | tx_id | Номер запроса 0..65535 |
| 6 | 1 | node | 13 или 14 |
| 7 | 1 | command | Код операции |
| 8 | 1 | status | В запросе 00; в ответе результат |
| 9 | 1 | idx | Индекс операции, либо FF для get_mode |
| 10 | 8 | data | Поля команды; неиспользуемые байты равны 00 |
| 18 | 2 | crc | CRC-16/CCITT-FALSE по байтам 2..17 |

CRC: polynomial 0x1021, init 0xFFFF, refin=false, refout=false, xorout=0. Контрольный пример ASCII `123456789` даёт 0x29B1. Magic в CRC не входит. Байты 03, 0C, 0D, 0A, A5 и 5A внутри data — обычные данные, без подмены и экранирования.

Новая версия не совместима со старой телеметрией из 29 байтов или обёртками CONTROL_REQUEST/CONTROL_RESPONSE. Автоматическое определение старого протокола и смешанный обмен не предусматриваются. Все узлы одной аппаратной цепочки должны перейти согласованно.

## Операции и маршрутизация

Размер data везде восемь байтов; в таблице показаны только значимые поля. Остальное — нули. Статус ошибки исключает интерпретацию data как успешного результата.

| Код | Метод | node | Доступ | idx | Запрос data | Успешный ответ data |
| --- | --- | ---: | --- | --- | --- | --- |
| 20 | get_temp | 13 | User | 0..1 | Нет | i32 температура в сотых °C, flags, u16 age_ms, 00 |
| 21 | get_voc | 13 | User | 0..1 | Нет | Зарезервирован; в v1 NOT_IMPLEMENTED |
| 22 | get_door_state | 13 | User | 0..1 | Нет | u8 closed, далее нули |
| 23 | get_pressure | 13 | User | 0..2 | Нет | u32 Па, flags, u16 age_ms, 00; пока NOT_IMPLEMENTED |
| 30 | get_pwm | 14 | User | 0..5 | Нет | u8 applied_pwm, далее нули |
| 31 | get_rpm | 14 | User | 0..5 | Нет | u32 rpm, далее нули |
| 32 | set_pwm | 14 | User | 0..5 | u8 pwm, далее нули | u8 applied_pwm, далее нули |
| 40 | get_mode | 14 | Admin | FF | Нет | u8 mode, u8 active_idx, далее нули |
| 41 | set_mode | 14 | Admin | 0..5 | u8 mode, далее нули | u8 mode, u8 active_idx, далее нули |
| 42 | set_door_lock | 14 | Admin | 0..1 | u8 lock_state, далее нули | u8 applied_lock_state, далее нули |

Коды command приведены в hex. Доступ User/Admin — граница программного интерфейса на ПК, а не отдельный транспортный флаг. Сырые кадры не предоставляются MCP как обходной инструмент. Хаб проверяет соответствие command/node; неизвестный код не угадывается по составу data.

Для get_mode idx=FF обязателен. Для set_mode idx должен быть 0..5, включая mode=0: при выключении режима допустимый idx игнорируется, выключается единственный активный сценарий. Это сохраняет предложенную сигнатуру set_mode(mode, idx). Результат mode=0 всегда содержит active_idx=FF, который на уровне API преобразуется в null.

## Числовые результаты и качество данных

Температура передаётся signed i32 в сотых °C: 25.50 → 2550, −0.25 → −25. Преобразование измерения в сотые — округление к ближайшему целому, половины от нуля. В JSON температура выражается числом в °C. Нормализация дробного байта старого протокола не используется.

Давление имеет единицу Па и формат unsigned u32. Драйвер BMP280 пока не подключается: текущая заглушка возвращает NOT_IMPLEMENTED. VOC также возвращает NOT_IMPLEMENTED; единица и формат успешного результата не назначаются до выбора датчика. Их добавление требует отдельного согласования контракта и версии, а не выдачи произвольного raw-числа под видом физической единицы.

RPM передаётся unsigned u32 в оборотах в минуту, без нормализации, подмены или ограничения общим максимумом. PWM — один байт 0..255. Bool — только 00 или 01; остальные значения являются INVALID_ARGUMENT.

Для температурного результата flags имеет бит 0 valid, бит 1 fresh; остальные биты нулевые. fresh=1 обязательно подразумевает valid=1. Возраст age_ms отсчитывается от завершения последнего корректного измерения до формирования ответа Arduino; при превышении 65534 мс насыщается до 65534. Невалидность передаётся ошибкой, а не успешным числом.

fresh означает новое успешное измерение, которое ещё не было включено в предыдущий успешный ответ get_temp для этого индекса. Повтор последнего значения имеет fresh=0; возраст продолжает расти. Это не условие температурной автоматики и не порог аварийного режима. Номер измерения/момент завершения должны сохраняться отдельно от времени выдачи ответа. Сервисное чтение GPIO или транспортная перепосылка не делают температуру свежей.

get_temp не ожидает преобразования DS18B20: при наличии прежнего корректного измерения возвращает его с возрастом и признаками; до первого корректного измерения возвращает SENSOR_UNAVAILABLE. Ошибка CRC датчика не превращает неудачное чтение в fresh=1 и не обновляет момент последнего успешного измерения. Если ранее было валидное измерение, оно может возвращаться с fresh=0 и возрастающим age_ms.

get_door_state возвращает true для закрытой двери, false для открытой. Электрическая полярность нормализуется в Arduino. idx одинаков для двери, концевика и замка.

## Семантика меняющих команд

Успех set_pwm означает, что выход Arduino был установлен, и содержит применённый PWM на момент формирования ответа. В mode=2 запрошенные 100 могут дать успешный ответ с applied_pwm=230. Это не подтверждение вращения вентилятора: RPM читается отдельно. Последующий тик mode=1 может изменить выход уже после ответа.

set_mode управляет единственным сценарием и возвращает его состояние. Повтор того же активного mode/idx не меняет PWM и не сбрасывает таймер. Новый сценарий отключает старый, сохраняя PWM прежнего вентилятора. mode=1 меняет PWM сразу, затем каждые 30 секунд; set_pwm применяется до следующего тика и не сдвигает расписание. mode=2 выбирает случайный PWM только при новой принятой set_pwm для выбранного вентилятора. Случайные целые равномерны на 0..255, совпадение с предыдущим значением допускается.

set_door_lock сообщает установленное командное состояние выхода замка. Это не обратная связь физического срабатывания замка или закрытия двери. Arduino не вводит решения по двери сверх выполнения команды.

На старте mode=0, все PWM=0, оба замка разблокированы. Потеря связи без перезапуска не сбрасывает выходы или сценарий. Выход из неисправности не восстанавливает прежнее запрошенное значение.

## Статусы

| Hex | Имя | Смысл |
| --- | --- | --- |
| 00 | OK | Успешный результат указанной команды |
| 01 | INVALID_INDEX | idx не разрешён для команды |
| 02 | INVALID_ARGUMENT | Аргумент, bool, mode или резервный байт неверен |
| 03 | UNKNOWN_COMMAND | Код операции неизвестен |
| 04 | NOT_IMPLEMENTED | Операция/драйвер предусмотрены, но ещё не реализованы |
| 05 | SENSOR_UNAVAILABLE | Реализованный датчик ещё не дал корректного значения |
| 06 | BUSY | Посредник не может принять новый обмен |
| 07 | DEVICE_TIMEOUT | Посредник не дождался нижележащего ответа |
| 08 | UNSUPPORTED_VERSION | CRC-корректный кадр известной длины имеет неподдерживаемую version |
| 09 | INTERNAL_ERROR | Внутренняя ошибка исполнения |
| 0A | REQUEST_ID_CONFLICT | Зарезервирован для будущей аппаратной дедупликации; в v1 не выдаётся |
| 0B | INVALID_NODE | Узел неизвестен или не соответствует команде |
| 0C | TRANSPORT_OVERFLOW | Обнаружено переполнение транспортной очереди |

Ответ ошибки сохраняет tx_id/node/command/idx запроса, использует version=1, kind=2 и восемь нулевых байтов data. Он имеет собственный корректный CRC. Ошибка индекса не заменяет idx на допустимый и не выполняет команду.

Порядок проверки полного CRC-корректного запроса: version → request status → известность command → соответствие node → idx → аргументы и резервные байты data → исполнение. Для неизвестного command применяется UNKNOWN_COMMAND, даже если его idx нельзя интерпретировать. Проверка корректности завершается до любых изменений выходов или режима.

Отказ по правам, неверный JSON-тип или число вне диапазона в User/Admin API обрабатываются на ПК до создания кадра. CRC-неверный/неполный кадр или неизвестный kind не получает ответа по недостоверным реквизитам; парсер восстанавливается, отправитель ограничивает ожидание своим тайм-аутом.

## Очередь, корреляция и повтор

Физический COM-порт принадлежит одному транспортному сервису. GUI, MCP и фоновый опрос передают запросы в одну FIFO-очередь. На всей цепочке разрешён один активный прикладной обмен; чтение датчиков не интерливится с управляющим запросом. Незапрошенная телеметрия в v1 не передаётся: ПК собирает снимок обычными методами.

tx_id назначает ПК, изменяет для каждого нового логического запроса и не сбрасывает при обычном переподключении в пределах процесса. Завершить запрос может только ответ с совпадающими version/kind/tx_id/node/command/idx. Запоздалый или чужой ответ журналируется и игнорируется. Сравнения только command или только status недостаточно.

Хаб принимает запросы только при отсутствии активного обмена. Если пришёл ещё один полный корректный запрос, он получает BUSY и не пересылается. BUSY для отклонённого запроса не должен перемешиваться с байтами другого ответа. Право передачи задаётся активным обменом: хаб разрешает ответ только выбранному шлюзу; шлюзы не передают самостоятельно. BUSY отправляется целым кадром после завершения или отмены разрешённого ответа, а не просто при кратковременном отсутствии байтов на линии. Входящие запросы не создают конкуренцию передатчиков.

Автоматических повторов меняющих операций нет ни на ПК, ни в хабе, ни в шлюзе. mode=2 делает повтор set_pwm новым воздействием; нельзя считать его идемпотентным только из-за совпадения аргументов.

Дедупликация повторного обращения MCP по decision_id реализуется будущим транспортным сервисом на ПК: повтор того же действия возвращает сохранённый результат/состояние и не создаёт новый аппаратный запрос. Повтор decision_id с другими аргументами отклоняется. Это относится к меняющим User-операциям и административным вызовам, не к запросам измерений.

Безответный запрос не означает «команда не выполнена». DEVICE_TIMEOUT, потеря ответа или переполнение после пересылки дают outcome=unknown для меняющей команды. Можно выполнить последующее чтение get_pwm/get_mode, но оно показывает текущее состояние и не доказывает причинность прошлого действия. Гарантии exactly-once через перезапуск оборудования или ПК в v1 нет.

Повтор чистого чтения допускается как новый запрос с новым tx_id после окончания старого обмена и восстановления транспорта. Номер не является секретом, административным разрешением или идентификатором измерения.

Ограничение проекта v1: после переполнения tx_id или запуска нового процесса старый ответ с повторно использованными tx_id/node/command/idx неотличим от нового. Единственный активный обмен сам по себе не решает эту проблему. Повторное использование номера требует гарантированного удаления прежних кадров из всей цепочки и подтверждённой верхней границы их времени жизни. До определения такой процедуры безопасное возобновление после wrap/перезапуска не специфицировано. Для строгой защиты потребуется идентификатор сессии/epoch в следующей редакции контракта.

## Временные ограничения и восстановление

Предлагаемые пределы прототипа отсчитываются локальными монотонными часами:

| Ограничение | Значение | Начало отсчёта |
| --- | --- | --- |
| Между принятыми прикладными байтами | 250 мс | Последний байт незавершённого кадра |
| Полный прикладной кадр | 1000 мс | Первый байт magic |
| Обработка Arduino | 500 мс | Приём полного корректного запроса |
| Обмен шлюз ↔ Arduino | 1500 мс | Шлюз принял полный запрос |
| Обмен хаб ↔ шлюз | 3000 мс | Хаб принял полный запрос |
| Ожидание ПК | 5000 мс | ПК закончил отправку полного запроса |

Ожидание в очереди ПК не расходует аппаратный тайм-аут; оно учитывается отдельно. Все разности времени должны корректно переживать переполнение millis. Верхний уровень не принимает новый запрос за продолжение старого.

По своему deadline каждый посредник отменяет нижележащий обмен и отбрасывает его поздние ответы, включая уже буферизированные. После восстановления старый ответ не пересылается как часть следующего обмена. Это обязательное правило будущей реализации, но не гарантия очистки произвольно остановленного и затем возобновлённого узла.

Парсер сохраняет максимум 20 байтов кандидата, ищет A5 5A и проверяет полный CRC. При неверном CRC поиск продолжается со следующего байта кандидата, включая возможное magic внутри его data. При межбайтовом/полном тайм-ауте частичный кадр отбрасывается. Финальный маркер не используется. Корректный CRC обнаруживает многие повреждения, но не является аутентификацией и не исключает случайную CRC-коллизию.

После аппаратного тайм-аута транспортный сервис отменяет состояние парсера и текущую корреляцию, дренирует вход и ждёт 250 мс тишины перед следующим обменом. Появление байта снова начинает это ожидание. Постоянная активность или отсутствие тишины не разрешают отправку следующей команды; соединение признаётся невосстановленным. После обычного переподключения выполняется такое же восстановление, а старые ожидающие меняющие запросы автоматически не воспроизводятся.

Тишина на линии ПК очищает локальный приём, но не доказывает отсутствие отложенного кадра в шлюзе или Arduino. Поэтому она не разрешает повторное использование tx_id после переполнения или перезапуска процесса.

## Ограничения существующих библиотек

Зафиксированная ревизия lapki-compiler — c0e235f364f21b1a7ba8dbb598ef0bc983511af6.

В [UART.hpp](https://github.com/kruzhok-team/lapki-compiler/blob/c0e235f364f21b1a7ba8dbb598ef0bc983511af6/compiler/library/tjc-ms1-main-a4/1.0/source/UART.hpp) SimpleBus использует кольцо на пять байтов без корректного обнаружения переполнения: безопасно только четыре непрочитанных байта. Обёртка не содержит адреса источника. В [arduino_link.c](https://github.com/kruzhok-team/lapki-compiler/blob/c0e235f364f21b1a7ba8dbb598ef0bc983511af6/compiler/library/tjc-ms1-ard-a1/1.0/source/arduino_link.c) очереди больше, но enqueue/RX также требуют обработки полного буфера. Сведения об этих местах проверены Terra по исходникам.

Будущая реализация должна явно обнаруживать переполнение, постоянно обслуживать RX и не использовать блокирующее ожидание всей операции в основном цикле. Полный кадр нельзя считать гарантированно доставленным потому, что удалось поставить байты в локальную очередь.

Между отправляемыми пятибайтовыми SimpleBus-пакетами предусматривается минимум 2 мс без блокировки обслуживания входа. При 9600 бод 8N1 один такой пакет занимает примерно 5.21 мс; двадцать пакетов — примерно 104.2 мс чистого времени линии. Ограничения времени включают промежуточные очереди и паузы; реальные значения нужно проверить на стенде.

Перед использованием [ArduinoAdapter.hpp](https://github.com/kruzhok-team/lapki-compiler/blob/c0e235f364f21b1a7ba8dbb598ef0bc983511af6/compiler/library/tjc-ms1-ard-a1/1.0/source/ArduinoAdapter.hpp) нужно проверить/исправить признак переполнения: текущая обёртка выставляет его при успешном enqueue и снимает при отказе. В шаге 1 библиотеки не исправляются; эти требования включаются в следующие этапы.

## Программный результат API

На уровне User/Admin API успешное чтение возвращает значение; температура дополнительно несёт valid/fresh и age_ms. Проект JSON-представления для будущих MCP tools:

```json
{"ok":true,"value":25.5,"unit":"degC","valid":true,"fresh":true,"age_ms":0}
```

```json
{"ok":true,"applied_pwm":230}
```

```json
{"ok":false,"error":{"code":"NOT_IMPLEMENTED"},"value":null}
```

```json
{"ok":false,"error":{"code":"DEVICE_TIMEOUT","outcome":"unknown"}}
```

NaN из заглушки не отправляется в JSON или как успешное числовое измерение на линию. Отсутствие реализации VOC/BMP280 отличается от валидного нулевого результата. Конкретный Rust-тип результата и полная MCP inputSchema будут реализованы на этапе API.

## Векторы и критерий завершения шага 1

Машиночитаемые векторы содержат полный request/response, значимые данные и отдельные случаи неверного CRC, обрыва, чужого ответа и сохранения специальных байтов. Они должны использоваться будущими реализациями C++ и Rust без независимого пересчёта ожидаемых байтов по их собственным кодировщикам.

Векторы содержат примеры успешных числовых значений и тестовые выборки RNG. Это заданные результаты проверки кодирования, а не показания стенда, не реализация драйверов BMP280/VOC и не фактические RPM конкретного вентилятора.

Шаг 1 подготавливает контракт и проверенные эталонные байты. Следующий шаг — реализация обработчиков по этому контракту; он не выполняется автоматически в этой работе.
